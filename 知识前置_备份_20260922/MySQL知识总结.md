## 1. 索引（Index）

### 1.1 为什么用 B+ 树？不用红黑树/哈希表？

**一句话结论**：B+ 树矮胖（高度 3-4 层可存千万级数据）、叶子节点有序且用链表相连，天然支持范围查询；非叶子节点只存索引不存数据，单节点能存更多 key，减少磁盘 IO。

追问链：
- 为什么不选红黑树？→ 树太高，千万级数据约 20+ 层，磁盘 IO 次数多
- 为什么不选哈希索引？→ 只支持等值查询 O(1)，不支持范围查询/排序
- B+ 树 vs B 树？→ B+ 树数据只在叶子、叶子有链表，范围查询更快、IO 更少

### 1.2 聚簇索引 vs 非聚簇索引（二级索引）

- **聚簇索引**：主键即索引，叶子节点存整行数据；一张表只能有一个
- **非聚簇索引**：叶子节点存主键值（不是数据行）；可多个
- **回表**：走二级索引查到主键 → 再回聚簇索引查整行数据

追问链：
- 为什么二级索引叶子存主键而非数据地址？→ 数据移动（页分裂）时不用改索引，且保证一致性
- 覆盖索引是什么？→ 查询的列都在索引里，无需回表（Extra 显示 Using index）
- 怎么避免回表？→ 建覆盖索引、少用 SELECT *

### 1.3 最左前缀原则

联合索引 (a,b,c)，查询必须从最左列开始才能命中：
- `WHERE a=?` ✅、`WHERE a=? AND b=?` ✅、`WHERE b=?` ❌（用不上索引）

追问链：
- 为什么要有最左前缀？→ B+ 树按索引列从左到右排序
- 把高频查询的列放最左边怎么选？→ 区分度高、等值查询的列优先

### 1.4 索引失效场景（高频）

- 对索引列用函数/运算：`WHERE YEAR(create_time)=2026`
- 隐式类型转换：`WHERE phone = 138...`（phone 是 varchar，传数字）
- 前导模糊查询：`LIKE '%abc'`（`'abc%'` 可以）
- `OR` 连接非索引列
- `NOT IN` / `!=`（视情况）

追问链：怎么验证索引生效？→ `EXPLAIN` 看 key 字段

## 2. 事务 ACID 与隔离级别

### 2.1 ACID 分别靠什么保证

- **原子性（Atomicity）**：undo log（回滚日志），失败回滚
- **一致性（Consistency）**：应用层 + 数据库约束共同保证
- **隔离性（Isolation）**：锁 + MVCC
- **持久性（Durability）**：redo log（重做日志），崩溃恢复

追问链：
- redo log 和 binlog 区别？→ redo 是 InnoDB 层物理日志（崩溃恢复）；binlog 是 Server 层逻辑日志（主从复制、恢复）
- 两阶段提交是什么？→ redo log prepare → binlog 写入 → redo log commit，保证两者一致

### 2.2 四种隔离级别

| 隔离级别 | 脏读 | 不可重复读 | 幻读 |
|---|---|---|---|
| 读未提交（RU） | ❌会 | 会 | 会 |
| 读已提交（RC） | ✅不会 | 会 | 会 |
| 可重复读（RR，MySQL 默认） | ✅ | ✅ | 基本解决（间隙锁） |
| 串行化（Serializable） | ✅ | ✅ | ✅ |

- **脏读**：读到别的事务未提交的数据
- **不可重复读**：同一行数据，两次读结果不同（另一个事务改了并提交）
- **幻读**：同一范围查询，两次读出的**行数**不同（另一个事务插入了新行）

追问链：
- MySQL 默认级别？为什么选 RR？→ RR（历史原因 + binlog 复制兼容性）；主流互联网常用 RC
- RR 怎么防幻读？→ 快照读靠 MVCC；当前读靠**间隙锁/临键锁**

## 3. MVCC（多版本并发控制）

**一句话结论（面试开场）**：MVCC = 多版本并发控制，靠"隐藏字段 + undo log 版本链 + ReadView"实现**快照读不加锁**，是 InnoDB 实现隔离性（RR/RC）的关键机制。

**常见误区（2026-08-02 踩坑）**：MVCC ≠ ACID。ACID 是事务四大特性；MVCC 只是实现其中"隔离性（I）"的一个机制（快照读）。**别把两者划等号**——自信地答错比"我不会"更伤可信度。

### 3.1 三个零件

1. **隐藏字段**（每行记录都有）：
   - `DB_TRX_ID`：最近修改该行的事务 ID
   - `DB_ROLL_PTR`：回滚指针，指向 undo log 中的上一版本
2. **undo log 版本链**：每次 UPDATE 生成新版本，旧版本经回滚指针串成链；沿链可找到任意旧版本
3. **ReadView（读视图）**：读操作时生成，记录判断可见性的快照：
   - `m_ids`：生成时仍活跃（未提交）的事务 ID 列表
   - `min_trx_id`：m_ids 中的最小 ID
   - `max_trx_id`：下一个将分配的事务 ID（上界）
   - `creator_trx_id`：创建该 ReadView 的事务 ID

### 3.2 ReadView 判定规则（背下来）

对版本链中某个版本的 `trx_id`：

1. `trx_id < min_trx_id` → 已提交，**可见**    min_trx_id 是最老活跃事务
2. `trx_id ≥ max_trx_id` → 在 ReadView 之后才开启的事务，**不可见**   max_trx_id 是最年轻的活跃事务
3. `min_trx_id ≤ trx_id < max_trx_id` → 查是否在 `m_ids` 里：在（未提交）→ **不可见**；不在（已提交）→ **可见** m_ids是活跃事务名单，如果在就证明是未提交的事务
4. 不可见就沿版本链找下一个，直到找到第一个可见版本

### 3.3 快照读 vs 当前读

- **快照读**（普通 SELECT）：MVCC 读，不加锁 → 快，读历史版本
- **当前读**（SELECT ... FOR UPDATE / UPDATE / DELETE）：读最新版本 + 加锁（记录锁/间隙锁/临键锁）→ 防并发写冲突

### 3.4 RC vs RR 的 ReadView（高频追问）

- **RC**：每次 SELECT 都新建 ReadView → 能看到别的事务新提交的数据 → 不可重复读
- **RR**：事务内第一次 SELECT 生成 ReadView 后**复用** → 每次读同一快照 → 可重复读 + 快照读无幻读

### 3.5 权衡（面试加分）

- 好处：读不加锁，读写不互斥，并发高
- 限制：写写冲突仍需锁；读到的是历史版本（快照语义，是**特性不是 bug**）；长事务导致 undo log 无法清理、版本链膨胀

追问链：
- MVCC 和间隙锁怎么分工？→ 快照读防幻读靠 MVCC；当前读防幻读靠间隙锁/临键锁
- 长事务为什么危险？→ ReadView 复用导致 undo log 无法清理，版本链长、占用空间
- 项目关联（短链接）：短码生成回写的写库事务在 RR 下，普通 SELECT 都是快照读——**读不被写阻塞**，这正是高并发读场景下缓存未命中回写能扛住的原因

## 4. 锁机制

### 4.1 分类

- **按粒度**：表锁、行锁（InnoDB 才有行锁）
- **按模式**：共享锁（S，读）、排他锁（X，写）
- **行锁细分**：
  - **记录锁（Record Lock）**：锁单行
  - **间隙锁（Gap Lock）**：锁区间，防插入 → 防幻读
  - **临键锁（Next-Key Lock）**：记录锁 + 间隙锁，默认 RR 下生效

追问链：
- 死锁怎么产生？→ 两个事务互持对方需要的锁，互相等待
- 怎么排查死锁？→ `SHOW ENGINE INNODB STATUS` 看 LATEST DETECTED DEADLOCK
- 怎么避免？→ 固定加锁顺序、缩小事务范围、索引要命中（避免锁升级为表锁）

### 4.2 意向锁

表级锁 + 行级锁的协调：加行锁前先加意向锁，避免全表扫描判断。

## 5. SQL 优化（简历承诺"索引优化"）

### 5.1 EXPLAIN 关键字段

| 字段 | 关注点 |
|---|---|
| type | system > const > eq_ref > **ref** > range > **index > ALL（全表扫描）** |
| key | 实际用的索引 |
| rows | 预估扫描行数，越小越好 |
| Extra | **Using index**（覆盖索引）✅ / **Using filesort**（文件排序，要优化）⚠️ / Using temporary（临时表）⚠️ |

### 5.2 慢 SQL 定位流程（追问链完整版）

1. 开慢查询日志：`slow_query_log=ON`，阈值如 `long_query_time=1`
2. 拿到慢 SQL → `EXPLAIN` 看 type/key/rows/Extra
3. 对症下药：缺索引 → 加；索引失效 → 改写 SQL；大 offset 分页 → 延迟关联/游标分页
4. 优化后对比执行时间与 rows

### 5.3 常用优化手段

- 分页深翻页：`LIMIT 100000,10` → 改 `WHERE id > 上次最大id LIMIT 10`（游标分页）
- 避免 `SELECT *`（回表 + 不必要 IO）
- 大字段/热点查询拆表
- 合理利用覆盖索引

## 6. 日志体系（进阶，加分项）

- **redo log**：物理日志，保证持久性（崩溃恢复），WAL 机制（先写日志再写数据）
- **undo log**：逻辑日志，保证原子性（回滚）+ MVCC 版本链
- **binlog**：Server 层逻辑日志，主从复制、数据恢复
- **两阶段提交**：redo prepare → binlog → redo commit

追问链：
- WAL 为什么快？→ 顺序写日志文件，避免随机写磁盘 + 合并刷盘
- 为什么需要 binlog 和 redo 两套？→ 一个在 InnoDB 层一个在 Server 层；主从复制用 binlog，崩溃恢复用 redo

## 7. 遇到不会的问题怎么答（保命指南）

**铁律：自信地答错 > 诚实说不会。** 面试官最恨的不是你不会，是你不懂装懂。

### 三种情况

1. **会一部分**：先给确定的部分，再明确边界。
   > "这部分我确定的是……；ReadView 的具体判定规则我记不全了，但我可以讲清楚版本链和隐藏字段……"
2. **完全不会但知道相关**：诚实 + 桥接（Adjacent Bridge）。
   > "这个问题我目前没深入掌握，不过我了解相关的 XX（讲相关的），这也是我接下来要补的。"
3. **完全不会也不相关**：诚实 + 展示思路，别硬编。
   > "这个我确实还没了解，但我可以按我熟悉的 XX 的思路来分析一下……"

### 三不要

- ❌ 不要蹦不确定的知识（自信地答错，Credibility 直接崩）——2026-08-02 踩过：把 MVCC 说成 ACID
- ❌ 不要说"我不会"就停（永远桥接 / 展示思路）
- ❌ 不要硬编一个不存在的例子（当场被拆穿）

### 脚本（背下来）

- 争取时间："这个问题让我组织一下——"（5 秒，比瞎说强）
- 承认边界："这块我不太确定，我讲一下我确定的……"
