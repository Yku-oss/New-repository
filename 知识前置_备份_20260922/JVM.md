## JVM（Java Virtual Machine）

> **一句话说清楚**：JVM 就是 Java 程序的"虚拟电脑"。你的 Java 代码不是直接跑在真实操作系统上的，而是跑在 JVM 这个"模拟电脑"里。所以同一个 `.class` 文件，Windows 上的 JVM 能跑，Linux 上的 JVM 也能跑——这就是 **"一次编写，到处运行"** 的秘密。

### 为什么需要 JVM？（给初学者的比喻）

想象你是个游戏玩家，你的游戏光盘（`.java` 源代码）不能在 PS5、Xbox、Switch 上直接通用。但如果你把游戏转成一种**中间格式**（`.class` 字节码），然后每台主机上都装一个"翻译器"（JVM），那你的游戏就能在所有平台上跑了。

```
你的代码 (.java)  →  javac编译  →  字节码 (.class)  →  JVM翻译  →  操作系统执行
                          ↑                          ↑
                    你写的代码                不同平台装不同版本的JVM即可
```

### Java 内存区域（Runtime Data Areas）

JVM 在运行时会把自己占用的内存划分成几个不同的"区域"，就像一栋楼分成不同的房间，每个房间有特定的用途。

| 区域 | 线程共享？ | 存什么东西？ | 会不会 OOM？ |
| --- | --- | --- | --- |
| **堆（Heap）** | ✅ 是 | **所有你 `new` 出来的对象、数组** | ✅ **最常见** |
| **方法区（Method Area）** | ✅ 是 | 类的结构信息（类名、方法、字段）、静态变量、常量 | ✅ 会 |
| **程序计数器（PC Register）** | ❌ 否 | 当前线程执行到哪一行字节码了 | ❌ **不会** |
| **虚拟机栈（VM Stack）** | ❌ 否 | 方法运行时需要的局部变量、中间计算结果 | ✅ StackOverflow / OOM |
| **本地方法栈（Native Method Stack）** | ❌ 否 | 调用 C/C++ 写的 `native` 方法时用 | ✅ 会 |
| **运行时常量池（Runtime Constant Pool）** | ✅ 是 | 类文件中的字面量和符号引用（编译时确定的常量） | ✅ 会 |
| **直接内存（Direct Memory）** | 不归 JVM 管 | NIO 操作时用的**堆外内存**，绕过 JVM 直接操作物理内存 | ✅ 会 |

> **初学者疑问**：什么是"线程共享"？
> - **线程共享** = 所有线程都能访问这个区域的数据。就像公司的公共冰箱，谁都能开。
> - **线程私有** = 每个线程有自己的独立副本，别的线程看不到。就像每个人自己的工位抽屉。

#### 每块区域详细解释

##### ① 堆（Heap）—— 最重要的区域

- **存什么**：所有你用 `new` 关键字创建的对象。比如 `new Student()`、`new ArrayList()`、`new int[100]`
- **特点**：
  - 是 JVM 中**最大**的一块内存
  - **所有线程共享**——堆里的对象可以被任何线程访问
  - 也是 **GC（垃圾回收）** 重点照顾的区域
- **OOM 原因**：不停地 `new` 对象，又不释放 → 堆满了 → OOM

##### ② 方法区（Method Area）—— 存放类的"图纸"

- **存什么**：每个类的**结构信息**（类名、方法名、字段名）、**静态变量**（`static` 修饰的变量）、**常量**（`final` 修饰的）、JIT 编译后的机器码
- **比喻**：堆里存的是"实物"（对象），方法区存的是"图纸"（类信息）
- **Java 8 变化**：Java 8 之前叫"永久代（PermGen）"，Java 8 之后改名为"元空间（Metaspace）"，并且**不再占用 JVM 堆内存，而是使用本地内存**

##### ③ 程序计数器（PC Register）—— 最小的区域，记录"看到哪一行了"

- **存什么**：当前线程正在执行的**字节码指令地址**（行号）
- **为什么需要**：CPU 会切换线程执行（时间片轮转），切换回来后要知道刚才执行到哪一行了
- **为什么不会 OOM**：因为每个线程只存一个数字（地址），内存占用极小且固定
- **比喻**：就像你看书时用的书签，每次被打断都能回来找到刚才看到哪一行

##### ④ 虚拟机栈（VM Stack）—— 方法调用的"记账本"

- **存什么**：每个方法被调用时都会创建一个**栈帧（Stack Frame）**，栈帧里包含：
  - **局部变量表**：方法里定义的变量（`int a = 1;` 中的 `a`）
  - **操作数栈**：计算时的"草稿纸"（比如 `a + b` 先把 a、b 压入栈，再弹出相加）
  - **动态链接**：指向运行时常量池中该方法的引用
  - **方法出口**：方法执行完后回到哪里

```java
public void A() {
    int x = 1;
    B();          // 调用 B，A 暂停，A 的栈帧留在栈底
    int y = 2;
}

public void B() {
    int m = 3;
    C();          // 调用 C，B 暂停，B 的栈帧在中间
}

public void C() {
    int n = 4;    // C 在最上面
}                 // C 执行完弹出 → 回到 B → B 执行完弹出 → 回到 A
```

```
栈顶                    ← 栈是"后进先出"的
┌─────────────┐
│  C() 的栈帧   │  ← 正在执行
├─────────────┤
│  B() 的栈帧   │  ← 等待 C 返回
├─────────────┤
│  A() 的栈帧   │  ← 等待 B 返回
└─────────────┘
栈底
```

- **StackOverflowError**：方法调用层次太深（比如递归没有终止条件），栈帧把栈撑爆了

##### ⑤ 本地方法栈（Native Method Stack）

- 和虚拟机栈类似，但它是给 **`native` 方法**用的（Java 调用 C/C++ 代码时用）
- 比如 `Object.hashCode()` 底层就是 native 的

##### ⑥ 运行时常量池（Runtime Constant Pool）

- 每个类编译后都有一个 **Class 文件常量池**，里面记录了类中用到的所有常量（字符串、数字等）
- 类加载时，这个常量池会被加载到方法区，变成**运行时常量池**
- **String.intern()**：可以把字符串放入常量池，下次相同的字符串直接复用

##### ⑦ 直接内存（Direct Memory）

- **不在 JVM 堆中**，而是直接操作操作系统的物理内存
- Java NIO（New IO）通过 `DirectByteBuffer` 使用直接内存
- **优点**：读写速度快（减少数据在 Java 堆和系统堆之间的拷贝）
- **缺点**：不受 `-Xmx` 控制，需要单独管理

### OOM（OutOfMemoryError，内存溢出）

> **通俗理解**：JVM 申请内存时发现**真的没钱了**，只能报错崩溃。

- JVM 内存耗尽，无法再分配新内存，抛出 `java.lang.OutOfMemoryError`
- **OOM 是 Error（错误），不是 Exception（异常）**——区别在于：
  - **Exception**：程序可以 try-catch 捕获并恢复（比如空指针、数组越界）
  - **Error**：一般捕获不了，JVM 已经没救了，程序直接崩溃退出

#### 不同区域的 OOM 表现

| 区域 | OOM 错误信息 | 常见原因 |
| --- | --- | --- |
| 堆 | `java.lang.OutOfMemoryError: Java heap space` | 对象太多，堆太小 |
| 方法区/元空间 | `java.lang.OutOfMemoryError: Metaspace` | 动态生成太多类（比如 CGLib 代理） |
| 虚拟机栈 | `java.lang.StackOverflowError`（不是 OOM 但类似） | 递归太深 |
| 直接内存 | `OutOfMemoryError: Direct buffer memory` | NIO 分配的堆外内存太多 |

## 一、类加载机制（Class Loading）

> **通俗理解**：你写的 `.java` 文件被编译成 `.class` 字节码后，JVM 不能直接运行——它需要先把 `.class` 文件"读进来"并解析成 JVM 能理解的数据结构。这个过程就叫**类加载**。

### 1. 类的生命周期（一个类从生到死的 7 个阶段）

```
加载 → 验证 → 准备 → 解析 → 初始化 → 使用 → 卸载
      └───── 连接（Linking）────┘
```

初学者只需要先记住前 5 步：

| 阶段 | 做什么？ | 比喻 |
| --- | --- | --- |
| **加载（Loading）** | 找到 `.class` 文件，把字节码读进内存 | 你从书架上拿一本书 |
| **验证（Verification）** | 检查字节码格式是否正确，有没有恶意代码 | 检查书的印刷质量、有没有缺页 |
| **准备（Preparation）** | 为**静态变量**分配内存并设置默认值（`int` 默认 0，`boolean` 默认 false） | 在桌上给书预留一个位置 |
| **解析（Resolution）** | 把类中用到的**符号引用**（比如类名 `String`）替换成**直接引用**（内存地址） | 把"找张三"变成"去 3 号楼 205 室找张三" |
| **初始化（Initialization）** | 执行静态代码块和静态变量赋值语句 | 打开书正式开始读 |

> ⚠️ **重要**：类加载的时机——不是程序一启动就加载所有类，而是**第一次主动使用**某个类时才加载（懒加载）。比如 `new` 对象、调用静态方法、访问静态字段。

```java
// 类的初始化时机示例
public class Demo {
    public static void main(String[] args) {
        // 此时 Student 类还没有加载！
        System.out.println("hello");
        // 直到下面这行，JVM 发现要用 Student 了，才去加载 Student.class
        Student s = new Student();  // ← 触发类加载
    }
}
```

### 2. 类加载器（ClassLoader）—— 谁负责加载类？

JVM 中有**3 个内置的类加载器**，还有程序员可以自己写的**自定义类加载器**。按"级别"从高到低排列：

| 加载器 | 谁来写的？ | 负责加载什么？ | 通俗比喻 |
| --- | --- | --- | --- |
| **启动类加载器（Bootstrap）** | **C++**（不是 Java） | `java.lang.*`、`java.util.*`、`rt.jar` 等**核心类库** | 国家图书馆（最权威，最底层） |
| **扩展类加载器（Extension）** | Java | `jre/lib/ext/` 目录下的扩展包 | 省市图书馆 |
| **应用程序类加载器（AppClassLoader）** | Java | **你自己写的代码** + 第三方 jar 包（Maven 依赖等） | 你家楼下的社区图书馆 |
| **自定义类加载器** | 你写 Java 代码 | 动态加载特殊路径下的类 | 你自己的私人书柜 |

### 3. 双亲委派模型（Parent Delegation Model）—— 核心机制

> **一句话**：**先让爹来，爹不行自己上。**

```
              Bootstrap ClassLoader（最顶级，C++写的）
                        ↑ 委派
              Extension ClassLoader
                        ↑ 委派
              Application ClassLoader（最常用）
                        ↑ 委派
              自定义 ClassLoader
```

#### 工作流程（配例子理解）

假设你的代码里写了 `String s = "hello";`，JVM 需要加载 `java.lang.String` 类：

```
1. 自定义 ClassLoader 接到加载 String 的请求
2. 自定义："我不加载，先问我爸"
   → AppClassLoader："我也不加载，先问我爸"
   → Extension ClassLoader："我也不加载，先问我爸"
   → Bootstrap ClassLoader："java.lang.String 是我负责的，我找到了！加载！"
3. Bootstrap 加载成功，String 类被加载到内存
```

#### 为什么要有双亲委派？—— 安全性！

**场景**：如果有人写了一个恶意的 `java.lang.String` 类并放在 classpath 下，会发生什么？

- **如果没有双亲委派**：AppClassLoader 会直接加载这个恶意 String，你的程序里所有 `String` 都是恶意的！—— **核心 API 被篡改**
- **有双亲委派**：String 的加载请求一直委派到 Bootstrap，Bootstrap 找到真的 `rt.jar` 中的 String 加载——**你写的假 String 永远不会被加载**

✅ **双亲委派的好处**：
1. **避免重复加载**：同一个类不会被加载两次
2. **安全**：核心 API 不会被篡改（`java.lang.String` 始终是 JDK 自带的那个）

### 4. 打破双亲委派（面试常问）

> 双亲委派是好机制，但有些场景下**必须打破它**。

#### 场景 ①：JDBC 驱动加载（SPI 机制）

```java
// JDBC 4.0 之后，可以通过 ServiceLoader 加载驱动
Connection conn = DriverManager.getConnection(url, user, password);
```

- `DriverManager` 是 `rt.jar` 里的核心类（由 Bootstrap 加载）
- 但 MySQL 驱动 `com.mysql.cj.jdbc.Driver` 是第三方 jar（AppClassLoader 才能加载）
- Bootstrap 找不到 MySQL 驱动 → **需要"反向"让 AppClassLoader 帮忙加载**
- **解决方案**：使用**线程上下文类加载器（Thread Context ClassLoader）**，它默认是 AppClassLoader

#### 场景 ②：Tomcat 隔离

- 一个 Tomcat 上可能部署了 10 个 Web 应用
- 每个 Web 应用可能用了**不同版本**的同一个 jar（比如 A 用 Spring 5，B 用 Spring 6）
- Tomcat 给每个 WebApp 一个**独立的类加载器**，优先加载自己 `WEB-INF/lib` 下的类
- **自己的 jar 自己负责，互不干扰**

#### 场景 ③：热部署

- 修改了代码后不想重启服务器，想让新的类生效
- 创建**新的自定义类加载器**加载新版本的类
- 旧的类加载器和旧的类对象可以被 GC 回收
```
个人总结 ：   JDBC 驱动加载，Bootstrap(启动加载类)扫描不到Mysql驱动时，可以通过线程上下文加载器（比如 启动类 反跳转到 扩展类）实现 
             Tomcat(汤姆猫)是通过给每一个 WebApp 提供独立的加载器，使得类加载时优先加载 'Web-INF/lib'下的类，实现了不同jar版本互不打扰运行（类似于App不同版本也能进行交流使用）
             热部署就是创建一个自定义类，直接插入运行的服务器中，加载类时让新的类生效，而旧的那一块直接被GC回收

```

## 二、对象创建与内存分配

> 当我们写 `new Student("张三", 18)` 时，JVM 在背后做了哪些事情？

### 1. 对象创建过程（7 个步骤详解）

```java
Student s = new Student("张三", 18);
```

当你写下这行代码时，JVM 做了以下事情：

```
① new 指令         → JVM 遇到 new 关键字
② 检查类是否已加载   → 检查 Student 类有没有被加载过，如果没有→先执行类加载
③ 分配内存         → 在堆中给 Student 对象划分一块内存空间
④ 初始化零值       → 把所有字段设为默认值（name=null, age=0）
⑤ 设置对象头       → 记录对象是哪个类的实例、哈希码、GC 年龄等
⑥ 执行 <init> 方法  → 调用构造方法 Student("张三", 18)，把"张三"和 18 赋值
⑦ 返回引用地址     → 把堆中对象的地址赋值给变量 s
```

> **给初学者的比喻**：就像你在网上订了一个定制蛋糕——
> ① 下单（new）
> ② 确认商家有没有这个款式（检查类加载）
> ③ 烤箱里给你腾出位置（分配内存）
> ④ 放上蛋糕胚（零值初始化）
> ⑤ 在蛋糕上标注"这是水果蛋糕"（设置对象头）
> ⑥ 加上水果和奶油（执行构造方法）
> ⑦ 送到你手上（返回引用）

### 2. 内存分配方式——怎么在堆里找空地？

JVM 在堆中给新对象分配内存时有两种方式，取决于堆内存是否**规整**：

| 方式 | 怎么做的？ | 什么时候用？ |
| --- | --- | --- |
| **指针碰撞（Bump The Pointer）** | 堆内存像一块平整的土地，只用"指针"标记哪里已用哪里未用。分配时直接把指针往后挪一个对象大小 | GC 使用**标记-整理**或**复制**算法后，内存是连续的 |
| **空闲列表（Free List）** | 堆内存像一块瑞士奶酪，到处是洞。JVM 维护一个列表记录哪些空闲区域可用，分配时找一块足够大的 | GC 使用**标记-清除**算法后，内存有碎片 |

```java
// 指针碰撞 比喻：停车场一辆接一辆停，新车直接停到最后一辆后面
// 空闲列表 比喻：停车场到处是空位，得找到够大的空位才能停

个人总结 ： 因为内存是连续的，所以指针碰撞就是两个内存就会连在一起
           空闲列表就是一个记录空闲的内存的列表，分配内存时JVM就会找一个足够大的区域装进去
```

### 3. 对象在内存中长什么样？（对象内存布局）

一个 Java 对象在堆内存中由**三部分组成**：

```
┌──────────────────────────────────┐
│         对象头（Object Header）     │ ← 固定大小（12字节或16字节，64位系统）
│  ┌────────────────────────────┐   │
│  │   Mark Word（标记字）        │   │ ← 存哈希码、GC年龄、锁状态（8字节）
│  ├────────────────────────────┤   │
│  │   Klass Pointer（类型指针）   │   │ ← 指向方法区中的类信息（4或8字节，指针压缩时4字节）
│  └────────────────────────────┘   │
├──────────────────────────────────┤
│         实例数据（Instance Data）    │ ← 真正的字段值（int、引用类型等）
│  比如 Student 的 name(String)      │
│         age(int)                 │
├──────────────────────────────────┤
│         对齐填充（Padding）          │ ← 保证对象总大小是 8 的倍数（JVM 要求）
└──────────────────────────────────┘
```
```
个人总结：
    一个Java对象在堆中（专门储存对应的数据），是由三部分组成的，
        一是对象头 ： 其中包括 Mark Word 储存字节哈希编码，锁的状态，GC的年龄；
        二是实例数据 ： int，String 与引用类型等
        三是对齐填充 ： 根据JVM要求，对象总是8的倍数

```
#### Mark Word 里存了哪些信息？（重点）

Mark Word 是对象头的核心，64 位系统下占 **8 字节（64 位）**，它**非常节省空间**——同一时刻只存一种信息：

| 对象状态 | Mark Word 中存储的核心内容 |
| --- | --- |
| **无锁** | 哈希码、分代年龄、偏向锁标志(0)、锁标志(01) |
| **偏向锁** | 线程ID、偏向时间戳、分代年龄、偏向锁标志(1)、锁标志(01) |
| **轻量级锁** | 指向栈中锁记录的指针、锁标志(00) |
| **重量级锁** | 指向 Monitor（管程）的指针、锁标志(10) |
| **GC 标记** | GC 标记信息、锁标志(11) |

> ⚠️ 一个对象刚创建时，哈希码是 0（没有计算过），只有在第一次调用 `hashCode()` 时才计算并写入 Mark Word。

### 4. 对象的访问定位——怎么找到对象？

当我们在代码中使用一个对象引用时：

```java
Student s = new Student();  // s 是栈上的引用变量，指向堆中的 Student 对象
s.getName();                // JVM 怎么通过 s 找到堆中的对象？
```

有两种实现方式：

| 方式 | 示意图 | 说明 | 谁在用？ |
| --- | --- | --- | --- |
| **句柄池** | `栈引用 → 句柄池 → 对象实例 + 类信息` | 栈中的引用指向**句柄池**（一块专门的内存），句柄池再指向堆中对象和方法区类信息 | 少数 JVM 实现 |
| **直接指针** | `栈引用 → 对象实例（对象头中有类型指针）` | 栈中的引用**直接指向堆中对象**，对象头中的 Klass Pointer 指向方法区类信息 | **HotSpot（Oracle JDK 默认）** |

**直接指针的优势**：少一次寻址，速度更快——这也是 HotSpot 选择它的原因。

```
直接指针方式：
栈                         堆                        方法区
┌──────┐              ┌────────────┐             ┌──────────┐
│  s   │──→ 地址 ──→  │ Mark Word  │──→ Klass ──→│ Student  │
└──────┘              │ Klass ptr  │             │ 类信息    │
                      │ name="张三" │             └──────────┘
                      │ age=18     │
                      └────────────┘
```

## 三、垃圾回收（GC - Garbage Collection）⭐ 高频面试

> **通俗理解**：Java 中 `new` 出来的对象不用了，你不需要手动释放内存——**JVM 会自动帮你去回收那些不再使用的对象**。这个自动回收的过程就叫垃圾回收（GC）。
>
> 但 GC 不是免费的——它需要暂停程序（STW），所以我们需要理解它，让它"少干活、干快活"。

### 1. 判断对象是否可回收——怎么知道一个对象"死了"？

GC 的第一步是判断哪些对象**已经没人用了**（可以回收）。

#### 方法一：引用计数法（Reference Counting）—— 简单但不好

**原理**：每个对象配一个计数器，被引用一次就 +1，引用失效就 -1。计数器为 0 就可以回收。

```java
// 引用计数法示例
Student a = new Student();  // a 对象的计数器 = 1
Student b = a;              // a 对象的计数器 = 2（b 也引用了 a）
a = null;                   // a 对象的计数器 = 1（a 不引用了，但 b 还在引用）
// 此时对象不会被回收，因为计数器还不为 0
```

**致命问题：循环引用**

```java
// 循环引用——引用计数法无法处理的场景
class Node {
    Node next;
}

Node a = new Node();   // a 的计数器 = 1
Node b = new Node();   // b 的计数器 = 1
a.next = b;            // b 的计数器 = 2（a 引用了 b）
b.next = a;            // a 的计数器 = 2（b 引用了 a）

a = null;              // a 的计数器 = 1（但 a 还被 b.next 引用着）
b = null;              // b 的计数器 = 1（但 b 还被 a.next 引用着）
// ⚠️ a 和 b 互相引用，计数器都不为 0，但实际上已经没人用它们了！
// 引用计数法认为它们还活着，不会被回收 → **内存泄漏**
```

> 所以 HotSpot（Oracle JDK 用的 JVM）**不使用引用计数法**。

#### 方法二：可达性分析（Reachability Analysis）✅ HotSpot 使用

**原理**：从一组**根对象（GC Roots）** 出发，像"蜘蛛网"一样往下搜索，能到达的对象就是"活的"，不能到达的就是"死的"。

```
        GC Roots                    堆中的对象
     ┌───────────┐
     │  main()   │──→ 对象 A ──→ 对象 B
     │ 线程引用   │       │
     │ 静态变量   │       └──→ 对象 C
     └───────────┘               │
                           └──→ 对象 D
                               
                               对象 E ← 没有从 GC Roots 出发的路径到达 → 可回收！
                               对象 F ← 也没有 → 可回收！
```
个人总结
```
   引用计数法： 就是bean对象计数器，如果被引入就会 +1，引入失效就会 -1，计数器为 0 就回收
   
   可达性分析： 从根对象 GC Roots (也就是main线程)出发，根据所遍历的类向下传输，如果路径可以到达的类与用到的对象bean，就证明不是无用对象，如果没有遍历到就是没有用的，那么就会将这部分的 bean 回收，减少内存占用。
```


**结论**：对象 E 和 F 虽然可能互相引用，但它们都"孤悬海外"，没有和 GC Roots 连通 → **判定为可回收**。

> 🔑 **核心记忆**：**引用计数法看"被引用了多少次"，可达性分析看"从根能不能走到"**。可达性分析**天然解决了循环引用问题**。

### 2. GC Roots 有哪些？（面试常背）

GC Roots 就是 JVM 中**肯定不会回收的对象**，作为搜索的起点。主要包括：

| GC Roots 类型 | 具体是什么？ | 举例 |
| --- | --- | --- |
| **① 栈帧中的局部变量** | 正在执行的方法里定义的变量 | `main()` 方法里的 `Student s = new Student()` 中的 `s` |
| **② 静态变量** | 类中用 `static` 修饰的变量 | `public static List<User> userList = ...` |
| **③ 常量** | `static final` 修饰的常量 | `public static final String APP_NAME = "myApp"` |
| **④ JNI 引用** | 本地方法（C/C++代码）中引用的 Java 对象 | Java 调用 C 代码时传过去的对象 |
| **⑤ 活跃线程** | 正在运行的 Thread 对象 | 每个 `new Thread()` 启动后都是活的 |

> **简单记忆**：**栈里引用的、静态变量引用的、常量的、native 方法引用的、活着的线程**——这五种对象不能回收。

### 3. 四种引用类型——控制对象的"死活程度"

Java 提供了 4 种引用强度，从强到弱排列：

```java
// 先看代码感受一下不同引用的写法
Student s = new Student();                    // ① 强引用
SoftReference<Student> soft = new SoftReference<>(new Student());  // ② 软引用
WeakReference<Student> weak = new WeakReference<>(new Student());  // ③ 弱引用
PhantomReference<Student> phantom = new PhantomReference<>(new Student(), referenceQueue); // ④ 虚引用
```

| 类型 | 强度 | 回收时机 | 日常用途 | 代码写法 |
| --- | --- | --- | --- | --- |
| **强引用（Strong）** | 💪💪💪 | **永不回收**——只要还有强引用指向对象，GC 永远不会回收它 | 99% 的场景，`new` 就是强引用 | `Student s = new Student()` |
| **软引用（Soft）** | 💪💪 | **OOM 之前回收**——内存不够了才回收，内存够就不回收 | 图片缓存、网页缓存（内存紧张时自动释放） | `SoftReference<T>` |
| **弱引用（Weak）** | 💪 | **下次 GC 必回收**——不管内存够不够，只要 GC 运行就回收 | ThreadLocal、WeakHashMap | `WeakReference<T>` |
| **虚引用（Phantom）** | 🫥 | **随时可能回收**——get() 永远返回 null，不能通过它获取对象 | 跟踪对象被回收的时间点（NIO 堆外内存清理） | `PhantomReference<T>` |

```
    个人总结 ：  一般情况下，创建出来的关键实例都是用强引入 new ，是不会被回收的 ； 
                如果是声明缓存的内容，那么一般用软引入（soft），当即将出现 OOM（缓存爆炸） 时就会回收缓存对象; 
                当我们创建了一些线程或者储存数据的表时，我们可以用弱引入（Weak），这样当下次线程再次启动的时候就会一定回收线程，避免浪费；
                当我们想观察对象在哪里回收，或者想释放堆外内存时，我们就可以用虚引用（Phantom），可以随时回收对象。
```

#### 软引用实战：图片缓存

```java
// 图片缓存：内存够就留着，内存不够就丢掉
Map<String, SoftReference<Bitmap>> imageCache = new HashMap<>();

// 加载图片
public Bitmap loadImage(String path) {
    SoftReference<Bitmap> ref = imageCache.get(path);
    if (ref != null && ref.get() != null) {
        return ref.get();  // 缓存命中
    }
    Bitmap bmp = loadFromDisk(path);       // 从磁盘加载
    imageCache.put(path, new SoftReference<>(bmp));
    return bmp;
    // 如果内存紧张，JVM 会自动回收 SoftReference 中的 Bitmap
    // 下次 get() 时返回 null，重新从磁盘加载即可
}
```

#### 弱引用实战：ThreadLocal

```java
// ThreadLocal 的 key 就是弱引用
// 防止线程池中线程存活时间过长导致内存泄漏
ThreadLocal<User> threadLocal = new ThreadLocal<>();
threadLocal.set(user);

// 使用完后务必 remove()
threadLocal.remove();  // 如果不 remove，ThreadLocalMap 中的 Entry 可能泄漏
```

### 4. 垃圾回收算法——GC 用什么方法"打扫卫生"？

GC 本质上就是"找出死对象，回收它们占用的内存"。有 3 种基础算法：

#### 算法 ①：标记-清除（Mark-Sweep）

```
回收前：  📦📦📦🗑️📦🗑️📦📦    （🗑️ = 死对象）
            ↓ 标记死对象
         📦📦📦🗑️📦🗑️📦📦    标记死对象为🗑️
            ↓ 清除
         📦📦  📦  📦📦       清除后内存有空隙（碎片）
```

| 优点 | 缺点 |
| --- | --- |
| 实现简单，速度相对快 | ❌ **内存碎片**——清除后留下很多小碎片，新的大对象可能找不到足够的连续空间 |

> **打个比方**：你把书架上的旧书扔了，但扔完后书架上的空位是东一块西一块的，想放一套大百科全书可能就放不下了。

#### 算法 ②：标记-复制（Mark-Copy）

```
把内存分成两块 A 和 B：
┌──────────┬──────────┐
│    A     │    B     │
│  📦📦🗑️📦│  (空)    │
└──────────┴──────────┘
        ↓ 把 A 中活着的 📦 复制到 B
┌──────────┬──────────┐
│    A     │    B     │
│  (空)    │  📦📦📦   │
└──────────┴──────────┘
        ↓ 清除 A 全部
┌──────────┬──────────┐
│    A     │    B     │
│  (空)    │  📦📦📦   │  ← 下次分配用 A
└──────────┴──────────┘
```

| 优点 | 缺点 |
| --- | --- |
| ✅ **无碎片**——所有存活对象紧挨着放 | ❌ **浪费空间**——需要留出一半的内存空着 |
| ✅ **分配快**——指针碰撞即可 | |

> **打个比方**：搬家时，把所有要带走的家具先搬到新家，旧房子里的家具全扔掉——新家家具排列整齐，但旧家也有一半空间是空着的。

#### 算法 ③：标记-整理（Mark-Compact）

```
回收前：  📦🗑️📦🗑️📦🗑️    （🗑️ = 死对象）
          ↓ 标记死对象
         📦🗑️📦🗑️📦🗑️
          ↓ 整理（把所有📦往一端移动）
         📦📦📦           ← 所有活着的对象紧凑排列
```

| 优点 | 缺点 |
| --- | --- |
| ✅ **无碎片** | ❌ **效率低**——需要移动所有存活对象，更新引用地址 |
| ✅ **空间利用率高**——不像复制算法要浪费一半 | |

> **打个比方**：超市货架上的商品有些过期了要下架，下架后剩下的商品往中间挪，让货架整齐——但挪商品本身需要花时间。

#### 算法 ④：分代收集（Generational Collection）—— 实际使用的终极方案

JVM 实际**不是只用一种算法**，而是把堆分成不同区域，"看菜下饭"：

| 区域 | 特点 | 用什么算法？ | 原因 |
| --- | --- | --- | --- |
| **新生代** | 对象**朝生夕死**（大多数对象活不过第一次 GC） | **标记-复制** | 存活对象少，复制成本低 |
| **老年代** | 对象**存活时间长** | **标记-整理** 或 **标记-清除** | 存活对象多，复制成本高，用整理/清除减少移动 |

> **一句话总结**：**新生代用复制（快），老年代用整理（省空间）**。

### 5. 堆内存结构（分代模型）—— 理解 GC 的"地图"

JVM 把堆内存分为**新生代（Young Gen）**和**老年代（Old Gen）**两大部分：

```
                       堆（Heap）
┌──────────────────────────────────────────────────────────────┐
│                        新生代（Young Gen）                      │  老年代（Old Gen）  │
│  ┌─────────────────────┐  ┌──────────┐  ┌──────────┐  │  ┌──────────────────┐  │
│  │      Eden           │  │  S0      │  │  S1      │  │  │                   │  │
│  │   （伊甸园）          │  │  (存活区) │  │  (存活区) │  │  │                   │  │
│  │  大部分对象首先在这   │  │          │  │          │  │  │                   │  │
│  └─────────────────────┘  └──────────┘  └──────────┘  │  └──────────────────┘  │
│                           8 : 1 : 1（默认比例）          │                        │
└──────────────────────────────────────────────────────────────┘
    Minor GC 发生在这里（频繁，快）             Full GC 可能发生在这里（少，慢）
```

#### 新生代详解——大多数对象的"出生地"

- **Eden（伊甸园）**：大多数 `new` 出来的对象首先在这里分配
- **Survivor 0（S0）** 和 **Survivor 1（S1）**：存放 GC 后存活下来的对象
- 默认比例：**Eden : S0 : S1 = 8 : 1 : 1**
  - 所以新生代可用空间 = Eden + 一个 Survivor = 90%（另一个 Survivor 作为复制目的地）

#### 对象的"一生"（关键流程）

```
① new 一个对象 → 放在 Eden 区
② Eden 满了 → 触发 Minor GC
③ 把 Eden + S0 中活着的对象 复制到 S1
④ 清除 Eden + S0（全是垃圾了）
⑤ 存活对象年龄 +1（从 0 变成 1）
⑥ 下次 Eden 又满了 → 重复，但这次从 S1 复制到 S0（来回倒）
⑦ 对象年龄达到阈值（默认 15）→ 从 Survivor 晋升到老年代
```

> **打个比方**：就像新员工（对象）先到公司大厅（Eden）等待分配工位。每过一段时间（Minor GC），还没分配到的实习生（垃圾对象）被清退，留下来的老员工（存活对象）搬到正式工位（Survivor），待了 15 年（晋升阈值）后获得终身员工资格，搬到老员工楼层（老年代）。

#### 相关重要概念

| 概念 | 解释 |
| --- | --- |
| **对象晋升（Promotion）** | 对象从新生代移到老年代 |
| **晋升年龄阈值** | 默认 **15**（因为对象头 Mark Word 中用 4 位存年龄，最大 15），可通过 `-XX:MaxTenuringThreshold` 修改 |
| **动态年龄判定** | 如果 Survivor 中**同龄对象总大小 > Survivor 的一半**，这批对象直接晋升老年代——不需要等到 15 岁 |
| **大对象直接进入老年代** | 超过 `-XX:PretenureSizeThreshold` 的大对象直接分配到老年代（避免在 Eden 和 Survivor 之间来回复制） |

### 6. Minor GC / Major GC / Full GC —— GC 的三种"规模"

| GC 类型 | 发生位置 | 触发条件 | 速度 |
| --- | --- | --- | --- |
| **Minor GC（Young GC）** | 新生代 | **Eden 区满了** | ⚡ **很快**（毫秒级） |
| **Major GC（Old GC）** | 老年代 | 老年代空间不足（CMS 收集器时） | 🐢 **较慢** |
| **Full GC** | **整堆 + 方法区/元空间** | 老年代满、空间分配担保失败、主动调用 `System.gc()`、Metaspace 不足 | 🐢🐢 **最慢（比 Minor GC 慢 10 倍+）** |

> **面试重点**：Minor GC 频繁是正常的（说明对象快速死亡和回收），但 Full GC 频繁就**有问题**了。

### 7. 垃圾回收器——不同的"保洁团队"

不同回收器的区别主要在**多线程/单线程、并发/停顿时长、适合多大的堆**。

#### 新手速览：先记这 3 个最常用的

| 回收器 | JDK 版本 | 特点 | 适合场景 |
| --- | --- | --- | --- |
| **Parallel GC** | JDK 8 **默认** | 多线程并行，追求**高吞吐量**（CPU 利用率高） | 后台计算、批处理（不关心单次停顿） |
| **G1** | JDK 9+ **默认** | 分区管理，**可预测停顿时间** | 大堆（6GB+），需要控制停顿时间（如 Web 服务） |
| **ZGC** | JDK 15+ 正式 | **极低停顿（<10ms）**，几乎不影响程序运行 | 超大堆（TB 级）、低延迟要求（如金融交易系统） |

#### 完整对比表

| 回收器 | 作用于 | 算法 | 线程 | 特点 | 适用场景 |
| --- | --- | --- | --- | --- | --- |
| **Serial** | 新生代+老年代 | 复制 + 标记-整理 | 🕐 **单线程** | 简单高效，没有线程切换开销 | 客户端（桌面应用）、单核 CPU |
| **ParNew** | 新生代 | 复制 | 🕐🕐 **多线程** | Serial 的多线程版本 | 配合 CMS 使用 |
| **Parallel Scavenge** | 新生代 | 复制 | 🕐🕐 **多线程** | **关注吞吐量**（`-XX:GCTimeRatio`） | 后台计算、数据分析 |
| **Parallel Old** | 老年代 | 标记-整理 | 🕐🕐 **多线程** | Parallel Scavenge 的老年代搭档 | 配套 Parallel 使用 |
| **CMS** | 老年代 | 标记-清除 | 🕐🕐 **并发** | **低停顿**（并发收集），JDK 9 标记废弃 | 响应时间优先的 Web 应用 |
| **G1** ⭐ | **整堆** | 分区+复制+整理 | 🕐🕐 **多线程** | **可预测停顿**，JDK 9+ 默认 | 大堆（6GB+），通用首选 |
| **ZGC** 🚀 | 整堆 | 染色指针+读屏障 | 🕐🕐 **几乎全并发** | **<10ms 停顿**，TB 级堆 | 超低延迟场景，JDK 15+ 正式 |

#### G1 的核心特性（面试常考）

> **G1（Garbage First）** 从 JDK 9 起取代 Parallel GC 成为默认回收器。

**① 分区管理**：不再分连续的新生代/老年代，而是把堆分成 **2048 个 Region**（每个 1MB~32MB）

```
G1 的堆（不是连续的两块，而是棋盘格）
┌────┬────┬────┬────┬────┬────┐
│ E  │ E  │ S  │ O  │ O  │ H  │     E = Eden
├────┼────┼────┼────┼────┼────┤     S = Survivor
│ O  │ E  │ E  │ O  │ O  │ O  │     O = Old
├────┼────┼────┼────┼────┼────┤     H = Humongous（大对象）
│ S  │ O  │ O  │ H  │ H  │ E  │
└────┴────┴────┴────┴────┴────┘
```

**② 可预测停顿**：可以设定 `-XX:MaxGCPauseMillis=200`（目标每次 GC 不超过 200ms），G1 会选择**垃圾最多的 Region**优先回收（所以叫"Garbage First"）。

**③ Mixed GC**：G1 的 GC 可以**同时回收新生代 + 部分老年代**，而不是像传统 GC 那样要么只收新生代，要么全堆 Full GC。

#### CMS 的缺点（为什么被 G1 取代？）

CMS 是 JDK 8 时代常用的低延迟回收器，但已被 JDK 9 标记废弃，主要原因：

1. **内存碎片**：使用**标记-清除**算法，回收后内存不连续，大对象分配时可能提前触发 Full GC
2. **浮动垃圾**：并发阶段程序仍在运行，新垃圾只能下次 GC 回收，可能导致 Concurrent Mode Failure
3. **CPU 敏感**：并发阶段占用 CPU，程序吞吐量下降
4. **Concurrent Mode Failure**：浮动垃圾太多时退化为 Serial Old（单线程 Full GC），停顿极长

> **一句话**：CMS 追求低停顿，但**不稳定**——一旦出问题反而造成更长的停顿。G1 在可控性和稳定性上更好。

## 四、JVM 调优（日常必用）

> **新手提示**：调优不是一上来就改参数。正确的顺序是：**先发现问题 → 再用工具定位 → 最后才调参数**。不要盲目照搬网上的配置。

### 1. 常用 JVM 参数（一定要理解每个参数是干什么的）

JVM 参数分三类：
- `-X` 开头：非标准参数（多数 JVM 都支持）
- `-XX` 开头：扩展参数（特定于 HotSpot）
- 其他：标准参数（`-version`、`-classpath`）

#### 内存相关参数（最常用）

| 参数 | 干什么的？ | 示例 | 注意 |
| --- | --- | --- | --- |
| `-Xms` | **堆的起始大小**（JVM 启动时分配多少堆内存） | `-Xms512m` | **推荐 = -Xmx**，避免扩容开销 |
| `-Xmx` | **堆的最大大小**（JVM 最多能用多少堆内存） | `-Xmx4g` | 最最常用的参数！ |
| `-Xmn` | **新生代大小** | `-Xmn2g` | 一般设为堆的 1/3 ~ 1/2 |
| `-Xss` | **每个线程栈的大小** | `-Xss256k` | 调小可以支持更多线程（默认 1M，通常 256k 够用） |
| `-XX:MetaspaceSize` | **元空间初始大小** | `-XX:MetaspaceSize=256m` | 太小会导致频繁 Full GC |
| `-XX:MaxMetaspaceSize` | **元空间最大大小** | `-XX:MaxMetaspaceSize=256m` | 不设置的话可能无限增长 |
| `-XX:SurvivorRatio` | Eden 与 Survivor 的比例 | `-XX:SurvivorRatio=8` | 默认 8（Eden:S0:S1=8:1:1） |
| `-XX:MaxTenuringThreshold` | 对象**晋升老年代的年龄** | `-XX:MaxTenuringThreshold=15` | 最大 15 |
| `-XX:PretenureSizeThreshold` | 超过多大直接进老年代 | `-XX:PretenureSizeThreshold=1m` | 大对象直接进老年代，避免复制开销 |

#### GC 相关参数

| 参数 | 干什么的？ |
| --- | --- |
| `-XX:+UseG1GC` | 使用 G1 回收器（JDK 9+ 默认） |
| `-XX:+UseParallelGC` | 使用 Parallel 回收器（JDK 8 默认） |
| `-XX:+UseZGC` | 使用 ZGC 回收器（JDK 15+） |
| `-XX:MaxGCPauseMillis` | G1 的目标停顿时间（默认 200ms） |
| `-XX:ParallelGCThreads` | 并行 GC 线程数 |

#### 日志与诊断参数（生产环境必开）

| 参数 | 干什么的？ |
| --- | --- |
| `-XX:+PrintGCDetails` | 打印 GC 详细信息 |
| `-Xloggc:/path/gc.log` | GC 日志输出到文件 |
| `-XX:+HeapDumpOnOutOfMemoryError` | **OOM 时自动 dump 堆快照**（救命参数！） |
| `-XX:HeapDumpPath=/data/dump/` | dump 文件存放路径 |
| `-XX:+PrintHeapAtGC` | 每次 GC 前后打印堆信息 |

### 2. 生产环境典型参数示例（完整 JVM 启动配置）

```bash
# ========== 堆设置 ==========
-Xms4g                     # 初始堆 4G（和 -Xmx 相等，避免运行时扩容）
-Xmx4g                     # 最大堆 4G
-Xmn2g                     # 新生代 2G（堆的一半）
-Xss256k                   # 每个线程栈 256K

# ========== 元空间 ==========
-XX:MetaspaceSize=256m     # 元空间初始 256M
-XX:MaxMetaspaceSize=256m  # 元空间最大 256M

# ========== GC 选择 ==========
-XX:+UseG1GC               # 使用 G1 回收器
-XX:MaxGCPauseMillis=200   # 每次 GC 停顿不超过 200ms

# ========== 诊断 ==========
-XX:+HeapDumpOnOutOfMemoryError          # OOM 时自动 dump
-XX:HeapDumpPath=/data/dump/             # dump 保存路径
-XX:+PrintGCDetails -Xloggc:/data/logs/gc.log  # GC 日志
```

> 💡 **怎么确定堆大小？**
> - 先不设参数跑起来，用 `jstat` 观察 GC 频率
> - 如果 Full GC 频繁 → 堆太小
> - 如果 Minor GC 频繁但每次回收很少 → 新生代太小
> - 一般建议：**堆不超过物理内存的 70%**，留出给操作系统和其他程序

## 五、JVM 命令行诊断工具（日常必备）

> 当程序变慢、卡死、OOM 时，这几把"瑞士军刀"能帮你快速定位问题。

### 工具速查表

| 工具 | 全称 | 一句话作用 | 最常用法 |
| --- | --- | --- | --- |
| `jps` | Java Process Status | **查看当前有哪些 Java 进程在跑** | `jps -l` 显示完整包名 |
| `jstat` | JVM Statistics Monitoring | **查看 GC 统计信息** | `jstat -gcutil <pid> 1000` 每秒输出一次 |
| `jmap` | JVM Memory Map | **生成堆 dump 快照**（分析内存泄漏） | `jmap -dump:format=b,file=heap.hprof <pid>` |
| `jstack` | JVM Stack Trace | **查看所有线程的栈**（定位死锁、卡顿） | `jstack <pid>` |
| `jinfo` | JVM Configuration Info | **查看 JVM 启动参数** | `jinfo -flags <pid>` |
| `jcmd` | JVM Command | **多功能瑞士军刀**（JDK 8+） | `jcmd <pid> help` 查看所有子命令 |

#### ① jps —— 先找到你的 Java 进程

```bash
# 找到正在运行的 Java 程序及其 PID（进程 ID）
jps -l
# 输出示例：
# 12345 com.example.demo.DemoApplication  ← 你的 Spring Boot 应用
# 23456 org.jetbrains.jps.cmdline.Launcher  ← IDE 自带的
```

#### ② jstat —— 看 GC 情况（最常用的排查工具）

```bash
# 每隔 1 秒输出一次 GC 统计
jstat -gcutil 12345 1000

# 输出说明：
# S0    S1    E      O      M     CCS    YGC     YGCT    FGC    FGCT     GCT
# 0.00  8.87  45.23  52.34  92.11  87.23  128     0.892   3      0.234    1.126
#  ↑     ↑     ↑      ↑      ↑      ↑      ↑       ↑       ↑      ↑        ↑
# S0使用率 S1使用率 Eden% 老年代% 元空间%   压缩类   YoungGC次数 耗时   FullGC次数 耗时  总耗时
```

**怎么看结果？**
- **YGC（Young GC）次数增长太快** → 新生代太小
- **FGC（Full GC）频繁** → 有问题！堆太小或内存泄漏
- **O 列（老年代）一直很高** → 对象释放不掉，可能有泄漏

#### ③ jmap —— OOM 时生成 dump 文件

```bash
# 生成堆 dump 文件（内存快照）
jmap -dump:format=b,file=/tmp/heap.hprof 12345

# 然后你可以用 MAT（Eclipse Memory Analyzer）或 VisualVM 打开分析
```

#### ④ jstack —— 线程卡死时看每个线程在干嘛

```bash
jstack 12345

# 输出中找这些关键字：
# "http-nio-8080-exec-1" #12 prio=5 os_prio=0 tid=0x... nid=0x...
#    java.lang.Thread.State: BLOCKED (on object monitor)  ← 在等锁
#    java.lang.Thread.State: WAITING (on object monitor)  ← 在等通知

```

### 实战排查：CPU 100% 怎么办？

```bash
# 步骤 1：找 CPU 最高的线程
top -H -p 12345   # Linux 命令，找出 CPU 占用最高的线程 TID（假设是 19664）

# 步骤 3：在 jstack 输出里找这个线程

# 输出会告诉你是哪行代码在疯狂跑！
```

## 八、面试进阶追问（基于知识点深挖）

> 以下是一面/二面中面试官可能基于你的回答**深入追问**的问题，提前准备好能大大加分。

### 🔥 内存区域深挖

1. **Java 8 为什么用元空间（Metaspace）替换永久代（PermGen）？**
   - 永久代大小固定，容易 OOM；元空间使用本地内存（Native Memory），只受物理内存限制
   - 永久代需要 GC 调优（`-XX:MaxPermSize`），元空间自动扩展
   - 字符串常量池在 Java 7 已移到堆中，Java 8 彻底移除永久代

2. **字符串常量池、运行时常量池、Class 文件常量池的区别？**
   - **Class 文件常量池**：每个 `.class` 文件中的字面量和符号引用
   - **运行时常量池**：类加载后将 Class 文件常量池解析到方法区
   - **字符串常量池**：JDK 7 后在堆中，存储 `String.intern()` 的字符串实例

3. **虚拟机栈和本地方法栈的区别？**
   - 虚拟机栈执行 Java 方法；本地方法栈执行 `native` 方法（C/C++）

4. **什么是栈帧（Stack Frame）？包含哪些部分？**
   - 局部变量表、操作数栈、动态链接、方法出口
   - 每次方法调用创建一个栈帧入栈，方法结束出栈

### 🔥 对象创建深挖

6. **对象创建时，内存是否一定是线程安全的？怎么解决？**
   - 不是。两个线程可能同时分配对象到同一地址
   - 解决方案：**CAS + 失败重试**（乐观锁）或 **TLAB**（本地线程分配缓冲，先到先得）

7. **什么是标量替换？**
   - 逃逸分析后，如果对象未逃逸，将对象拆解为成员变量直接在栈上分配，不再创建对象

8. **对象头 Mark Word 在不同锁状态下的结构？**

| 锁状态 | Mark Word 存储内容 |
| --- | --- |
| 无锁 | 哈希码 + 分代年龄 + 偏向锁位(0) |
| 偏向锁 | 线程ID + Epoch + 分代年龄 + 偏向锁位(1) |
| 轻量级锁 | 指向栈中锁记录的指针 |
| 重量级锁 | 指向管程（Monitor）的指针 |
| GC 标记 | 空（前 30 位用于 GC 标记） |

### 🔥 GC 深挖（最容易被追问）

9. **什么是 Stop-The-World（STW）？哪些阶段会 STW？**
   - STW：所有用户线程暂停，只让 GC 线程工作
   - **必定 STW**：GC 初始标记、复制/整理阶段
   - **并发阶段**：并发标记、并发清除（CMS/ZGC 尽量减少 STW）

10. **什么是三色标记算法？CMS 有什么问题？**
    - **白色**：未扫描 | **灰色**：已扫描自身，未扫描引用 | **黑色**：已扫描完成
    - **CMS 的问题**：并发标记时，黑色对象引用被删除 → 白色对象不可达（本该回收）→ **浮动垃圾**
    - **解决方案**：**增量更新（Incremental Update）**：CMS 将黑色对象变回灰色重新扫描

11. **G1 用什么替代了三色标记？**
    - **SATB（Snapshot-At-The-Beginning）**：在并发标记开始时拍快照，期间引用变化记录在 SATB 队列中
    - 优点：更保守、更安全，比增量更新更容易实现并发

12. **G1 的 RSet（Remembered Set）是什么？**
    - 每个 Region 都有一个 RSet，记录**从其他 Region 指向本 Region 的引用**
    - 作用：Mixed GC 时不需要全堆扫描，只需扫描 RSet 就能知道跨 Region 引用
    - 代价：占用额外内存（约堆大小的 5%~20%）

13. **什么是 Humongous 对象？G1 怎么处理？**
    - 超过 Region 大小 50%（默认 Region ≈ 1MB~32MB）的对象
    - 直接分配到连续的多个 Humongous Region，不再进入 Eden/Survivor
    - 如果大对象过多，会频繁触发 Full GC（G1 的弱点之一）

14. **CMS 为什么会有 Concurrent Mode Failure？怎么解决？**
    - CMS 在并发标记/清理时，老年代空间被浮动垃圾占满，无法为新对象分配
    - **后果**：退化为 Serial Old（单线程 Full GC），停顿极长
    - **解决**：提前触发 CMS（`-XX:CMSInitiatingOccupancyFraction=70`），降低触发阈值

15. **JDK 17 默认的垃圾回收器是什么？**
    - JDK 9~16：G1（默认）
    - JDK 17+：仍然是 G1（ZGC 需要 `-XX:+UseZGC` 启用）
    - JDK 21+：ZGC 开始支持分代模式（Generational ZGC）

### 🔥 调优排查深挖

16. **老年代频繁 Full GC，可能是什么原因？**
    - 内存泄漏（对象无法回收）
    - 堆太小（`-Xmx` 设置过小）
    - 大对象直接进入老年代（`-XX:PretenureSizeThreshold` 设置过小）
    - 晋升失败（空间分配担保失败）

17. **GC 频繁但吞吐量低，你怎么调优？**
    - 增大堆内存（`-Xmx`、`-Xmn`）
    - 选择合适的 GC 器（响应优先用 G1/ZGC，吞吐优先用 Parallel）
    - 调整新生代比例（`-XX:SurvivorRatio`）
    - 检查是否有大对象

18. **生产环境如何定位死锁？**
    ```bash
    jstack <pid> | grep -A 30 "deadlock"    # 或直接看 "Found one Java-level deadlock"
    ```

19. **堆外内存（Direct Memory）怎么排查泄漏？**
    - 堆外内存不归堆管，`jmap` 看不到
    - 使用 `-XX:MaxDirectMemorySize` 限制大小
    - 用 `pmap`（Linux）或 `jcmd <pid> VM.native_memory` 看

### 🔥 并发与锁深挖

20. **偏向锁为什么在 JDK 15 默认关闭？**
    - 偏向锁的撤销需要 STW，在高并发场景下维护成本高
    - JDK 15+ 默认 `-XX:-UseBiasedLocking`，JDK 21 已移除代码

21. **重量级锁的 Monitor 依赖了什么？**
    - 操作系统的 **Mutex Lock（互斥量）**，涉及用户态→内核态切换，开销大

22. **synchronized 和 ReentrantLock 的底层区别？**
    - synchronized：JVM 层面（Monitor），自动释放锁
    - ReentrantLock：JDK 层面（AQS + CAS），需要手动 unlock
    - ReentrantLock 支持：可中断、公平锁、条件变量（Condition）

### 🔥 综合大问题

23. **从 new 一个对象到使用完毕被 GC 回收，描述完整的生命周期？**
    ```
    new → 类加载检查 → 分配内存（TLAB/Eden）→ 零值初始化 → 设置对象头 → 执行构造方法
    → 使用中（强/软/弱/虚引用）→ Eden 满 → Minor GC（复制到 Survivor）
    → 年龄 15 → 晋升老年代 → 老年代满 → Full GC（标记-整理/清除）→ 空间回收
    ```

24. **为什么 G1 不适合小堆（<4GB）？**
    - Region 数量不足（<2048），分区优势不明显
    - RSet 占用内存比例更高，小堆下开销占比大
    - **小堆推荐**：Parallel GC 或 Serial GC

25. **Java 的强/软/弱/虚引用在实际项目中怎么用的？请举例**
    - **软引用**：图片缓存（内存不足自动释放）
    - **弱引用**：`ThreadLocal` 的 Key（GC 后自动清理 Entry）、`WeakHashMap`
    - **虚引用**：`DirectByteBuffer` 的 Cleaner（堆外内存回收通知）
