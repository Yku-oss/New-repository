# Redis 知识总结

## 一、Redis 是什么

Redis（Remote Dictionary Server）是一个**基于内存**的 **Key-Value 非关系型数据库**，单线程模型（6.0+ 引入多线程处理网络 IO，但命令执行仍是单线程）。

### 为什么快？
```
    ① 基于内存：内存读写速度是磁盘的 10 万倍以上
    ② 单线程：避免了多线程上下文切换和锁竞争
    ③ IO 多路复用：一个线程监听多个 socket 连接（epoll）
    ④ 高效数据结构：跳表、压缩列表等
    ⑤ 命令简单：没有复杂的关系型查询
```

### 适用场景
| 场景 | 说明 | 举例 |
|------|------|------|
| 缓存 | 减轻数据库压力 | 热点数据、会话 Session |
| 计数器 | 原子自增 | 点赞数、访问量、库存预扣 |
| 排行榜 | ZSet 按分数排序 | 热销榜、积分榜 |
| 分布式锁 | SETNX | 秒杀、并发写保护 |
| 消息队列 | List / Stream | 简单异步任务 |
| 分布式 Session | 共享登录态 | 多实例共享 |

### 不适用场景
- 复杂的关系型查询（多表 join、复杂事务）→ 用 MySQL
- 海量冷数据存储（内存太贵）→ 用 HBase/OSS
- 强事务一致性要求 → 用关系型数据库

## 二、五大基础数据结构

### 1. String（字符串）
```
    底层编码：int / embstr（短串） / raw（长串）

    常用命令：
        SET key value       设置值
        GET key             获取值
        SETNX key value     不存在才设置（分布式锁基础）
        INCR / DECR         自增 / 自减（原子操作）
        INCRBY key n        加 n
        EXPIRE key 秒       设置过期时间
        SET key value EX 30 设置值 + 30 秒过期（原子）

    适用场景：
        · 缓存对象（JSON 序列化）
        · 计数器（INCR 原子性，如点赞、访问量）
        · 分布式锁（SETNX + EX）
        · Session 共享
```

### 2. List（列表）
```
    底层编码：quicklist（压缩列表 + 双向链表）

    常用命令：
        LPUSH / RPUSH     左/右插入
        LPOP / RPOP       左/右弹出
        LRANGE key 0 -1   取所有元素
        LLEN              长度
        BLPOP             阻塞弹出（可当消息队列）

    适用场景：
        · 简单的消息队列（LPUSH + BRPOP）
        · 最新消息列表（如朋友圈时间线）
        · 关注列表
```

### 3. Hash（哈希）
```
    底层编码：ziplist（小数据） / hashtable

    常用命令：
        HSET key field value     设置字段
        HGET key field           获取字段
        HGETALL key              获取所有字段
        HDEL key field           删除字段
        HINCRBY key field n      字段自增

    适用场景：
        · 存储对象（用户信息：name、age、email）
        · 购物车（user_id → 商品 id → 数量）
        · 比 String 省内存：不需要整体序列化反序列化
```

### 4. Set（集合）
```
    底层编码：intset（整数集合） / hashtable

    常用命令：
        SADD / SREM      添加 / 删除
        SMEMBERS         获取所有元素
        SISMEMBER        判断是否存在
        SCARD            元素个数
        SINTER           交集（共同好友）
        SUNION           并集
        SDIFF            差集
        SPOP             随机弹出（抽奖）

    适用场景：
        · 去重（唯一访客）
        · 共同好友 / 共同关注（SINTER 交集）
        · 抽奖（SPOP 随机弹出）
        · 标签系统
```

### 5. ZSet（有序集合）
```
    底层编码：ziplist（小数据） / skiplist（跳表）+ hashtable

    常用命令：
        ZADD key score member   添加成员 + 分数
        ZRANGE key 0 -1         按分数升序取
        ZREVRANGE key 0 -1      按分数降序取（排行榜）
        ZSCORE key member       获取分数
        ZINCRBY key n member    成员分数加 n
        ZRANK key member        排名
        ZREM key member         删除

    适用场景：
        · 排行榜（热销榜、积分榜）
        · 延时队列（score 存到期时间戳）
        · 限流（滑动窗口）
        · 优先队列
```

### 六大数据类型总结
| 类型 | 底层结构 | 典型场景 |
|------|---------|---------|
| String | int/embstr/raw | 缓存、计数器、分布式锁 |
| List | quicklist | 消息队列、时间线 |
| Hash | ziplist/hashtable | 对象存储、购物车 |
| Set | intset/hashtable | 去重、共同好友、抽奖 |
| ZSet | skiplist+hashtable | 排行榜、延时队列 |
| Stream（6.0+） | rax 树 | 专业消息队列（消费组） |

## 三、持久化

Redis 是内存数据库，数据默认在内存，**必须配置持久化**防止宕机丢数据。

### 1. RDB（快照持久化）
```
    原理：定期把内存数据生成二进制快照 dump.rdb

    触发方式：
        · 手动：SAVE（阻塞）/ BGSAVE（fork 子进程，不阻塞）
        · 自动：配置 save 900 1（900 秒内 1 次修改就保存）

    优点：
        · 文件小，恢复速度快
        · 适合做备份、迁移
    缺点：
        · 可能丢数据（两次快照之间的修改丢失）
        · fork 子进程时可能短暂阻塞
```

### 2. AOF（追加日志持久化）
```
    原理：把每条写命令追加到 appendonly.aof 文件

    刷盘策略：
        · appendfsync always：每条命令都刷盘（最安全，最慢）
        · appendfsync everysec：每秒刷盘（推荐，丢 1 秒数据）
        · appendfsync no：交给操作系统（最快，最不安全）

    AOF 重写：日志越来越大 → 重写压缩成最小命令集

    优点：
        · 数据安全性高（最多丢 1 秒）
    缺点：
        · 文件大，恢复慢
```

### 3. 生产实践
```
    RDB + AOF 混用：
        · AOF 保证数据不丢（everysec）
        · RDB 用于快速恢复和备份
        · 重启时优先加载 AOF（数据更全）

    面试题：Redis 重启后数据加载顺序？
        → 优先 AOF（更完整），没有 AOF 才加载 RDB
```

## 四、缓存三大问题（必问）

### 1. 缓存穿透（Cache Penetration）
```
    定义：查询一个【不存在】的数据，缓存和数据库都没有
         每次请求都直接打到数据库，DB 压力巨大

    攻击示例：恶意请求不存在的商品 id（-1、随机数）

    解决方案：
        · 方案一：缓存空值
            查不到数据也缓存 null，设置短过期时间（30-60 秒）
            → 简单有效，但会缓存大量空 key
        · 方案二：布隆过滤器（Bloom Filter）
            请求先过布隆过滤器，不存在直接返回，不进 DB
            → 高效，但有小概率误判（存在不一定真存在）
        · 方案三：参数校验
            非法 id（<=0、非数字）直接拦截
```

### 2. 缓存击穿（Cache Breakdown / Hotspot Invalid）
```
    定义：某个【热点 key】过期瞬间，大量并发请求同时打到数据库

    区别：穿透是查不存在，击穿是查存在的热点 key 恰好过期

    解决方案：
        · 方案一：互斥锁（Mutex）
            只让一个线程去查库重建缓存，其他线程等待
            Redis SETNX 加锁，重建完成后释放
        · 方案二：逻辑过期
            缓存里不设物理过期时间，value 里存逻辑过期时间
            发现逻辑过期 → 异步线程去刷新缓存，直接返回旧值
            → 实现复杂（需封装），但不会阻塞请求
```

### 3. 缓存雪崩（Cache Avalanche）
```
    定义：大量 key 【同时过期】或 Redis 宕机
         导致海量请求瞬间打到数据库，DB 被打垮

    解决方案：
        · 方案一：过期时间打散
            给过期时间加随机值（基础时间 + 随机数）
            避免大量 key 同时过期
        · 方案二：多级缓存
            本地缓存（Caffeine）+ Redis，Redis 挂了还有本地
        · 方案三：Redis 高可用
            主从 + 哨兵 / 集群，避免单点故障
        · 方案四：限流降级
            网关限流，DB 扛不住时降级返回兜底数据
```

### 三大问题对比
| 问题 | 定义 | 核心解决 |
|------|------|---------|
| **穿透** | 查不存在的数据 | 布隆过滤器 / 缓存空值 |
| **击穿** | 热点 key 过期瞬间 | 互斥锁 / 逻辑过期 |
| **雪崩** | 大量 key 同时过期 / 宕机 | 过期时间打散 / 多级缓存 / 高可用 |

## 五、分布式锁

### 为什么需要分布式锁？
```
    单体应用：synchronized / ReentrantLock（JVM 内有效）
    分布式系统：多个服务实例，JVM 锁失效
        → 需要跨进程的锁：Redis 分布式锁
```

### 1. 基本实现（SETNX + EX）
```
    加锁：
        SET lock_key unique_id NX EX 30
        · NX：不存在才设置（保证只有一个线程抢到）
        · EX 30：30 秒自动过期（防止死锁）
        · unique_id：当前线程唯一标识（UUID）

    解锁：
        // 必须先校验是自己的锁，再删除（Lua 脚本保证原子性）
        if redis.call("get", KEYS[1]) == ARGV[1] then
            return redis.call("del", KEYS[1])
        else
            return 0
        end

    为什么要用 Lua？
        → GET 和 DEL 不是原子操作，可能"删了别人的锁"
        → Lua 脚本在 Redis 中原子执行
```

### 2. 三个经典问题

| 问题 | 场景 | 解决 |
|------|------|------|
| **死锁** | 加锁后进程挂了，锁不释放 | SET 带过期时间 EX，自动释放 |
| **误删别人的锁** | 锁过期后 A 的锁被 B 抢到，A 执行完 DEL 把 B 的锁删了 | value 存唯一 ID，删除前校验 |
| **锁过期业务没完成** | 业务执行超过 30 秒，锁自动释放，其他线程进来了 | Redisson 看门狗自动续期 |

### 3. Redisson 看门狗（Watch Dog）
```
    原理：
        · 默认锁有效期 30 秒
        · 后台守护线程每 10 秒检查一次
        · 锁还被持有 → 自动把有效期续到 30 秒
        · 业务执行完 → 释放锁，看门狗停止

    好处：不用手动设置过期时间，锁不会提前失效

    代码：
        RLock lock = redissonClient.getLock("order_lock");
        lock.lock();                // 默认 30 秒，看门狗自动续期
        try {
            // 业务逻辑
        } finally {
            lock.unlock();          // 释放
        }
```

### 4. RedLock（红锁，了解）
```
    问题：主从架构下，主节点加锁后还没同步到从节点就挂了
         从节点顶上，锁丢了 → 两个线程同时拿到锁

    RedLock 方案：
        · 向 N 个独立 Redis 节点（≥3）尝试加锁
        · 超过一半节点（N/2+1）加锁成功才算成功
        · 加锁时间 < 锁有效期才有效

    争议：RedLock 在复杂网络下仍有理论缺陷，生产可用性存疑
         多数场景用"单节点 + 看门狗 + 主从"已足够
```

## 六、过期删除与内存淘汰

### 1. 过期删除策略
```
    Redis 采用：惰性删除 + 定期删除 结合

    · 惰性删除：访问 key 时才检查是否过期，过期就删
        → 省 CPU，但过期 key 可能残留占内存
    · 定期删除：每 100ms 随机抽查一批 key，删除过期的
        → 折中方案，防止残留太多

    为什么不实时删除？
        → 每删除一个 key 都要阻塞，性能差
    为什么不只靠惰性删除？
        → 过期 key 不访问就永远占内存
```

### 2. 内存淘汰策略（maxmemory-policy）
```
    Redis 内存满时，8 种淘汰策略：

    · noeviction（默认）：不淘汰，直接报错（写命令失败）
    · allkeys-lru：从所有 key 中淘汰【最近最少使用】（推荐）
    · allkeys-lfu：从所有 key 中淘汰【最不经常使用】
    · allkeys-random：随机淘汰
    · volatile-lru：从【设置了过期时间】的 key 中淘汰 LRU
    · volatile-lfu：从过期 key 中淘汰 LFU
    · volatile-random：从过期 key 中随机淘汰
    · volatile-ttl：淘汰【即将过期】的 key

    LRU vs LFU：
        · LRU：最近最少用（看时间）
        · LFU：最不经常用（看频率），防"冷门 key 偶尔用一次"被误杀

    记忆锚（2026-08-04 练习加的）：
    总体分noeviction + 4种算法 × 2个范围（volatile / allkeys）= 8种
    LRU = 最近最少用（时间） LFU = 最不经常用（频率） random = 随机淘汰 TTL = 即将过期
        4 种算法（LRU / LFU / random / TTL）× 2 个范围（volatile 只动过期的 / allkeys 全库）
        + noeviction（不淘汰报错）= 8 种
        生产常用：allkeys-lru 或 volatile-lru
```

## 七、高可用架构

### 1. 主从复制（Master-Slave）
```
    结构：一个主节点（写）+ 多个从节点（读）

    原理：
        · 全量复制：从节点第一次连接，主节点生成 RDB 快照同步
        · 增量复制：后续通过复制积压缓冲区同步命令
        · 复制偏移量 + 运行 ID 保证不丢

    作用：
        · 读写分离（主写从读，分摊压力）
        · 数据备份
        · 主挂了从可以顶上（配合哨兵）

    缺点：主节点挂了，需要人工切换（或哨兵）
```

### 2. 哨兵模式（Sentinel）
```
    结构：主从 + 哨兵进程监控

    作用：
        · 监控：定期检查主从节点是否存活
        · 自动故障转移：主节点挂了 → 自动选一个从节点升为主
        · 通知：通知客户端新的主节点地址

    原理：
        · 哨兵之间通过发布订阅互相通信
        · 主观下线（一个哨兵认为挂了）→ 客观下线（多数哨兵确认）
        · 选举新主：从节点中选一个（优先级高、数据新、runid 小）

    生产配置：至少 3 个哨兵（防止哨兵单点）
```

### 3. Cluster 集群（Cluster）
```
    结构：多个主从对，数据分片存储

    分片原理：
        · 16384 个哈希槽（slot）
        · key 通过 CRC16(key) % 16384 计算落到哪个槽
        · 每个主节点负责一部分槽位（如 3 主：5461 / 5462 / 5461）

    特点：
        · 数据分布在不同节点，容量水平扩展
        · 每个主节点可以挂从节点（高可用）
        · 客户端直连任意节点，节点间互相转发（MOVED 重定向）
        · 多 key 操作需要同一个 slot（用 hash tag：{user1}）

    缺点：
        · 不支持多 key 跨节点事务
        · 迁移槽位时可能有短暂不可用
```

### 4. 三种模式对比
| 模式 | 数据分片 | 高可用 | 容量扩展 | 适用场景 |
|------|:-------:|:------:|:-------:|---------|
| 主从 | ❌ | 手动 | ❌ | 小规模，读写分离 |
| 哨兵 | ❌ | ✅ 自动 | 只能垂直 | 中小规模，需要自动切换 |
| 集群 | ✅ | ✅ | ✅ 水平 | 大规模，数据量超过单机 |

## 八、缓存与数据库一致性

### 问题场景
```
    更新数据库后，缓存还是旧数据 → 读到了脏数据

    常见方案：
    · 先更新数据库，再删除缓存（推荐）
    · 先删缓存，再更新数据库（并发下容易脏）
    · 延迟双删：先删缓存 → 更新 DB → 延迟 500ms 再删一次
    · 订阅 binlog（Canal）异步删缓存（最可靠，无侵入）
```

### 为什么"先更新 DB 再删缓存"而不是"先更新缓存"？
```
    · 写频繁场景：直接更新缓存会导致大量无效写（缓存可能马上被淘汰）
    · 删除缓存：下次读时 miss，重新查库加载，天然"懒加载"
    · 删除比更新简单，且不会引入数据不一致

    风险：删缓存失败怎么办？
        → 重试机制（消息队列重试 / 延迟双删兜底）
```

### 最终一致性方案对比
| 方案 | 复杂度 | 一致性 | 说明 |
|------|:------:|:------:|------|
| 先更库再删缓存 | 低 | 较高 | 主流，删失败需补偿 |
| 延迟双删 | 低 | 高 | 加 500ms 延迟兜底 |
| binlog 订阅（Canal） | 高 | 最高 | 无侵入，异步解耦 |

## 九、高级特性

### 1. Redis 事务
```
    MULTI        开启事务
    命令1...
    命令2...
    EXEC         执行事务

    特点：
        · 命令队列化，EXEC 时按顺序执行
        · 不支持回滚（一条失败，其他照常执行）
        · 没有隔离级别概念（命令间无查询）

    注意：Redis 事务很弱，复杂场景用 Lua 脚本
```

### 2. Lua 脚本
```
    原理：一段 Lua 脚本在 Redis 中原子执行（中间不会被其他命令打断）

    场景：
        · 分布式锁的原子"校验 + 删除"
        · 库存扣减的原子"检查 + 扣减"
        · 多个命令需要原子执行

    示例（原子扣库存）：
        local stock = redis.call("get", KEYS[1])
        if tonumber(stock) > 0 then
            return redis.call("decr", KEYS[1])
        end
        return -1
```

### 3. 管道（Pipeline）
```
    原理：一次网络请求发送多条命令，减少 RTT（网络往返）

    场景：批量写入、批量查询
    注意：管道不是事务，只是批量发送
```

### 4. 布隆过滤器（Bloom Filter）
```
    原理：多个哈希函数映射到位数组，判断"一定不存在"或"可能存在"

    特性：
        · 判断不存在 → 一定不存在（绝不漏报）
        · 判断存在 → 可能不存在（有误报率）

    场景：
        · 缓存穿透防护（拦截不存在的 key）
        · 黑名单、URL 去重

    使用：
        Redis 4.0+ 通过布隆过滤器模块：BF.ADD / BF.EXISTS
```

### 5. 发布订阅（Pub/Sub）
```
    SUBSCRIBE channel      订阅频道
    PUBLISH channel msg    发布消息

    缺点：消息不持久化，发布时没有订阅者就丢失
    替代：Stream（支持消费组，消息持久化）
```

### 6. 大 key 与热 key（生产必问）
```
    大 key 问题：
        · 单个 key 的 value 过大（>10KB 或元素 >1 万）
        · 危害：阻塞命令、内存不均、删除阻塞
        · 解决：拆分大 key（分段存储）、用 Hash 拆字段

    热 key 问题：
        · 某个 key 被大量请求访问（如爆款商品）
        · 危害：单节点压力大、缓存击穿风险
        · 解决：多级缓存、key 加后缀分散到多节点（副本）
```

### 💡 高频追问
```

    → 先更库再删缓存 + 延迟双删 + 消息重试兜底

    · Redis 挂了怎么办？
    → 哨兵自动切换 / 多级缓存兜底 / 限流降级

    · 为什么用 Redis 做分布式锁而不用 ZooKeeper？

      用专业 MQ（RocketMQ/Kafka）
```
