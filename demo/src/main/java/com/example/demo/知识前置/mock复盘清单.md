### ❌ 讲的不好（重点改）

**1. ⚠️⚠️ 防超卖说成"先加锁，再判断库存"（第二次犯！）**
- **错误原话**："第二层就是先用行锁锁住要下单的商品，然后判断库存是否大于0"
- **问题**：这是 **check-then-act 的思路**（先锁再查再改 = 3 步）→ **正好是超卖的根源**
- **正确**：**判断和扣减在同一条 SQL 里**
  ```sql
  UPDATE seckill_goods SET stock = stock - 1 WHERE id = ? AND stock > 0
  ```
  **`UPDATE` 执行时 InnoDB 自动加行锁**（不是"我主动加锁"）
- **口诀**：**"一条 UPDATE，不是三步"**。说成"先锁再判断"= 自己暴露 check-then-act
- **⚠️ 两次都错在这** → 必须背成条件反射

**2. ⚠️ MQ 可靠性只答了 1/3（漏最关键的"死信队列"）**
- **错误原话**："三次都处理失败了就会抛出异常，后面可以转为人工操作进行后续处理"
- **问题**：
  - ❌ **没说"死信队列（DLQ）"** → 面试官会追问"消息在哪等人工处理？"→ **答不上**
  - ❌ 只说消费者层，**漏生产者（confirm）和 Broker（持久化）层**
  - ❌ 没提"我怎么验证的"（实测过：`Retries exhausted` → DLQ 消息 0→1）
- **标准答法（三层）**：
  > ① **生产者**：队列 durable 持久化；
  > ② **Broker**：消息落盘；
  > ③ **消费者**：auto ack + **重试 3 次**（1s/2s/4s 指数退避）→ **重试耗尽 → reject → 经死信交换机（DLX）转进死信队列（DLQ）**，不丢，可人工/定时补偿。
  > 我实测验证过：故意抛异常 → 日志 `Retries exhausted` → DLQ 消息数 +1。
- **口诀**：**"重试耗尽 → 死信队列"是固定搭配，必须一起说**

**3. ⚠️ Docker 概念混淆："将中间件一起打包"**
- **错误**：听起来像"MySQL 和应用打进了同一个镜像"
- **正确区分**：
  | 概念 | 做什么 | 产物 |
  |---|---|---|
  | **打包** | 把**应用**变成镜像 | `Dockerfile` → `seckill-app:1.0` |
  | **编排** | 把**多个容器**组织起来 | `docker-compose.yml` |
- **正确说法**："应用**打成镜像**；中间件用 **Compose 编排**（各自独立容器）"
- **其他错词**："依赖分离"（含糊）、"重新配置 docker 的依赖"（不是概念）

**4. ⚠️ Redis 预热追问：没区分"启动时"和"运行中"**
- **面试官问**："运行中 Redis 挂了重启，库存怎么办？"
- **错误答**："通过预热让数据不丢失"
  - ❌ **预热只在应用启动时跑一次** → **Redis 运行中挂了，预热不会重跑** → **救不了**
  - ❌ "不丢失"不准确 → 应是**"可重建"**（缓存丢了能从 DB 重建，≠ 不丢）
- **标准答法（分情况 + 诚实说边界）**：
  > ① **应用重启时** → `CommandLineRunner` 重跑预热 → 自动恢复 ✅
  > ② **Redis 运行中挂了（应用不动）** → **我的预热救不了**（只跑一次）
  > **改进方向**：加**定时任务**定期刷 DB→Redis；或 **RDB/AOF 持久化**；或 **哨兵/集群**做高可用。
  > 目前是基础版，生产还需要持久化 + 高可用配合。
- **心法**：问"XX 挂了怎么办"，要答三层 —— **预防**（持久化/高可用）+ **恢复**（预热/定时同步）+ **兜底**（DB 是数据源）

**5. 项目介绍开头啰嗦**
- **错误**："我做的这个秒杀项目，作用是在活动期间时，具有防止超卖，一人一单的功能..."
- **问题**：名词堆砌（"作用""功能"），前 15 秒都在绕；"这个项目要用了"（多字）
- **改法**：**第一句直接给"核心矛盾 + 核心方案"**
  > "秒杀项目核心解决**高并发下的超卖**。我用**两层防线**：..."
- **还漏了**：量化结果（压测 0 超卖）+ 新增功能（超时取消/MQ可靠性/Docker）
- **错词**："信息管道" → 应为 **"消息队列"**

**6. 订单超时取消：漏了核心机制"延迟队列没有消费者"**
- **缺**：**"延迟队列故意不配消费者"** ← 这才是"延迟"的本质，面试官会追问
- **缺**：流程闭环（死信后 → 死信交换机 → **超时处理队列** → 消费者取消+回补库存）
- **表述模糊**："占用数据" → 应说"**库存被长期占用**"；"影响线程" → 没说清（用 sleep 会阻塞消费线程）

## 第二次 mock（2026-09-21）

### ❌ 讲得不好的（重点改）

**1. 项目介绍——没有主线（罗列功能）**
- 问题：按功能罗列（超卖→MQ→Redis→令牌桶），听不出主次；**丢了最核心的"防超卖两层方案"**
- 改法：**先讲核心（防超卖两层）→ 再讲配套（一人一单/限流/MQ）**
- 标准开场：
  > "秒杀项目核心解决**高并发超卖**，我用**两层防线**：第一层 Redis+Lua 预减挡流量；第二层 MySQL 条件更新+行锁兜底。配套做了**一人一单**（唯一键兜底）和**令牌桶限流**防刷；下单用 **MQ 异步削峰**。"

**2. ⭐ 防超卖两层——只答了 DB 层，漏了 Redis 层**
- 问题：问"两层防线"，只说了"行锁+stock>0"（那是第二层），**第一层 Redis+Lua 没说**
- 标准答法（**必须两句话都说**）：
  > "**第一层**：Redis + Lua 脚本原子预减库存——读库存、判断够不够、够就 DECRBY，**挡流量**；
  > **第二层**：MySQL 条件更新 `UPDATE ... SET stock=stock-1 WHERE id=? AND stock>0`——**行锁**保证原子、`stock>0` 条件保证不为负，做**最终兜底**。"

**3. 说错词："削谷" → 应为"削峰"**
- 削峰 = 削掉流量洪峰（MQ 把请求排队慢慢处理）
- ⚠️ 这个说错很扎眼（之前也犯过）

**4. 缓存击穿方案——把 Redis 锁说成"行锁"**
- 击穿的**互斥锁**是 **Redis 分布式锁**，不是 MySQL 行锁
- 混淆点：**行锁（MySQL）≠ 分布式锁（Redis）**

### ✅ 讲得好的（保持）

- 缓存穿透/击穿/雪崩：**三个定义全对**（方案有 1 处混淆）
- 事务失效（同类调用绕过代理）：**答对**
- 线程池扩容（核心满→队列→队列满→扩容到 max）：**答对**
- MyBatis 返回类型（int=影响行数 / 对象=取字段）：**答对**
