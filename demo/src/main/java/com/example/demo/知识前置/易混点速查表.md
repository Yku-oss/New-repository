## 一、Spring

### 1. 三级缓存 vs 事务失效 ⚠️（最容易串）
| | 解决什么问题 | 内容 |
|---|---|---|
| **三级缓存** | **循环依赖**（A↔B）| 一级成品/二级早期引用/三级工厂 |
| **事务失效** | @Transactional 不生效 | 同类调用/private/吞异常 |

> 一句话：**三级缓存 → 循环依赖**；**事务失效 → 拆类/public/抛异常**。别串。

### 1b. ⭐⭐ 三级缓存为什么是"三级"（2026-09-27 回炉通过）

| 级别 | 名字 | 存什么 |
|---|---|---|
| **一级** | `singletonObjects` | **完整成品 Bean** |
| **二级** | `earlySingletonObjects` | **早期引用**（属性还没注入、@PostConstruct 还没跑） |
| **三级** | `singletonFactories` | **ObjectFactory 工厂**（⚠️ **存的是 lambda/工厂，不是对象**） |

> ⚠️ **别叫"半成品"，说"早期引用"**（2026-09-28 纠正）：二级/三级装的不是同类东西 ——
> 三级是**函数**，二级是**函数执行后的结果**。面试说"早期引用"更专业。

**为什么要三级？→ 为了 AOP 代理**

**只用二级会怎样（后果链）**：
```
① 暴露出去的是【原始对象 A_raw】
② B 注入的是 A_raw
③ A 最终被 AOP 包装成【代理对象 A_proxy】
④ ❌ B 里的 A_raw ≠ 容器里的 A_proxy → 不一致
⑤ ❌ B 调用 A 的方法时【绕过事务/切面】
```

**三级（工厂）怎么解决**：
```
① A 创建到一半 → 把【工厂 lambda】放进三级缓存
② B 需要 A → 调工厂 → getEarlyBeanReference()
   → 判断 A 需要 AOP 吗？
      · 需要 → 【现在】生成代理，放入二级
      · 不需要 → 返回原始对象
③ B 拿到的 = 容器最终的 ✅（且代理只生成一次）
```

> **核心**：**三级存工厂 = "延迟决策"** —— 只在真被循环依赖引用时，才决定要不要提前生成代理，**且只生成一次**。

**构造器注入的循环依赖能解决吗？** → ❌ **不能**
- 因为构造器注入**必须在创建实例时传入依赖** → 对象还没生出来 → **无法提前暴露**
- Spring 直接抛 `BeanCurrentlyInCreationException`
- **字段注入 / setter 注入** → ✅ 能解决（先创建对象再填属性，可提前暴露）

### 2. 事务失效 vs 缓存三大问题
| 看到什么词 | 答哪套 |
|---|---|
| "事务失效 / @Transactional" | 同类调用 / private方法 / 吞异常 |
| "缓存 / Redis 穿透击穿雪崩" | 穿透(查不存在) / 击穿(热点key过期) / 雪崩(大量key同时过期) |

## 二、Redis

### 3. LRU vs LFU ⚠️
| | 看什么 | 淘汰谁 | 英文 |
|---|---|---|---|
| **LRU** | **时间** | 最**久**没被访问 | Least **Recently**(最近) Used |
| **LFU** | **次数** | 最**不经常**使用 | Least **Frequently**(频繁) Used |

> 记忆：**LRU 看时间，LFU 看次数**。"最不经常使用"只属于 LFU。

### 4. 过期删除 vs 内存淘汰（易混）
| | 触发 | 干嘛 |
|---|---|---|
| **过期删除** | key 到期时 | 惰性删除 + 定期删除 |
| **内存淘汰** | 内存满了 | 8 策略（noeviction/allkeys-lru/...）|

### 5. TTL 命令 vs volatile-ttl 策略
| | 是什么 |
|---|---|
| TTL 命令 | 查一个 key 还剩几秒（查询），不是删 |
| volatile-ttl | 内存满时删"快过期"的 key（淘汰策略）|

### 5b. allkeys vs volatile 范围 ⚠️（2026-09-19 混淆过）
- **allkeys** = 所有 key 都在淘汰范围
- **volatile** = **只管"设置了过期时间的 key"**（不是"快过期"！）
- ⚠️ 曾把 volatile 说成"快过期"——错。**"快过期"是 `volatile-ttl`**（淘汰最快过期的那个）
- 8 种 = 4算法(lru/lfu/random/ttl) × 2范围(allkeys/volatile) + noeviction；ttl 只有 volatile 版

## 三、MySQL

### 6. 间隙锁四场景锁 ⚠️
> RR + 当前读下：
- **唯一索引命中** = 行锁
- **唯一索引没命中** = 间隙锁
- **非唯一索引命中** = 行锁 + 间隙锁
- **范围查询** = 临键锁（记录锁 + 间隙锁）

### 6b. ⭐⭐ MVCC vs 当前读（2026-09-27 回炉通过，之前理解反了）

**RR 下读分两条路**：

| | **快照读** | **当前读** |
|---|---|---|
| 语句 | 普通 `SELECT` | `FOR UPDATE` / `UPDATE` / `DELETE` |
| 读什么 | **ReadView 可见的【旧】版本** | **最新版本 + 加锁** |
| 靠什么 | **MVCC**（undo log 版本链） | **锁**（间隙锁/临键锁） |
| 负责 | **可重复读** | **更新正确 + 防幻读** |
| 会幻读吗 | ❌ **不会**（看不见新行） | ✅ 会 → 靠**间隙锁**防插入 |

- ⚠️ **曾错**："MVCC 读最新版本" ← **反了**。MVCC 读的是**历史快照版本**
- ⚠️ **别混**：**"可重复读"只靠 MVCC 实现**，**当前读不参与**（它每次看最新，本来就不是"可重复"的）

**MVCC 原理（三层）**：
```
行隐藏字段：DB_TRX_ID(最后修改的事务ID) + DB_ROLL_PTR(回滚指针 → undo log)
undo log 串成【版本链】：当前行 → 旧版本 → 更旧版本
读取时：沿版本链从新到旧找【第一个对 ReadView 可见】的版本
```

**RC vs RR 的唯一区别 = ReadView 生成时机**：
| 级别 | 生成时机 | 效果 |
|---|---|---|
| **RC（读已提交）** | **每次 SELECT 重新生成** | 能看到别人新提交的 |
| **RR（可重复读）** | **事务内只生成一次** | 前后读一致（可重复读） |

> 口诀：**RC 每次拍新照片；RR 只拍一张，后面都看这张。**
> 口诀：**快照读靠 MVCC（看不见）；当前读靠间隙锁（插不进）。**

**"可见"的简化规则**（版本 trx_id vs ReadView 的 m_ids）：
- trx_id < m_ids 最小值 → ✅ 可见（已提交）
- trx_id 在 m_ids 里 → ❌ 不可见（未提交）
- trx_id > m_ids 最大值 → ❌ 不可见（快照后才开始）

### 7. MyBatis 返回类型

|---|---|---|
| INSERT/UPDATE/DELETE | int | 影响行数 |
| SELECT 单条要字段 | 对象 | 取字段 |
| SELECT COUNT(*) | int | 是个数 |

### 8. 唯一键 vs 索引 ⚠️（2026-09-15 混淆过）
- **唯一键** = **防重复**（约束该列不能重复，重复插入报 DuplicateKeyException）
- **索引** = **加快查询**
- 两个目的不同，别混。

### 9. 接口幂等（结果：重复执行结果不变）
- **状态机**幂等：`UPDATE ... AND status=0`（状态不对→更新0行→不执行）
- **唯一键**幂等：`uk_order_no`（重复插入报错→只产生一单）—— DB层最终兜底
- 实现方案：唯一键 / 幂等令牌 / 状态机 / 分布式锁

### 10. ⭐⭐ 索引为什么"失效"（2026-09-28 抽查答成 1/10）

**根因（记这一句就够了）**：
> **优化器做成本估算 —— 发现全表扫描更便宜时，主动放弃索引。**

**触发条件（3 类）**：
| 类型 | 例子 | 为什么 |
|---|---|---|
| **区分度低 / 返回行多** | `WHERE age=20` 命中 20% 的行 | 回表 20 万次（随机IO）> 顺序扫全表 |
| **列上有运算 / 函数** | `WHERE age+1=21`、`WHERE YEAR(t)=2026` | B+树按【原始值】排序，运算后无法二分查找 |
| **隐式类型转换** | `varchar` 列传数字 `20` | 要转换才能比 → 索引可能失效 |

**其他**：`OR` 连了无索引列 / `LIKE '%xx'`（前置 %）/ 统计信息过期（`ANALYZE TABLE`）

**⚠️ 纠正一个因果反了的说法**：
- ❌ "命中就走索引" ← 因果反了
- ✅ 优化器【先估算成本】，再【选择】走不走索引

**面试话术**：
> "'索引失效'更准确的叫法是'优化器主动放弃索引'。它会估算回表成本，
> 当要返回的数据占比很高（经验值 >20%）时，【回表 + 随机IO】的成本
> 高于【全表顺序扫描】，就会放弃索引。"

## 四、其他易混锚点
- **间隙锁(MySQL)** vs **行锁防超卖**：防超卖用 `AND stock>0` 条件更新(行锁)，不是间隙锁
- ⚠️ 反复犯：扣库存**永远说"行锁 + AND stock>0 条件"**，**不许说"间隙锁"**（间隙锁是另一个概念：RR下范围查防插入）
- ⚠️ 别用错词：并发扣减不是"脏读"；第二个失败是 UPDATE影响0行(不是"事务回滚")
- **事务/Redis 单线程/代理**这些"关键词"要先识别属于谁再答

### 秒杀"双层防超卖"分工 ⭐（项目核心卖点，面试必问）
| 层 | 判断什么库存 | 目的 |
|---|---|---|
| **Redis + Lua** | **Redis 缓存里**的库存 | **挡流量**（保护 DB）|
| **DB 行锁 + stock>0** | **数据库里**的库存 | **最终兜底**、以 DB 为准 |
- 只用 DB：流量大会打爆；只用 Redis：可能丢数据/不一致 → 故两层都要
- **Redis 预减成功但 DB 扣失败 → 两层不一致** → 靠"对账 / 回补"。这是秒杀经典取舍（Redis 乐观预减，DB 最终裁决），能主动说出=加分

### 🚨 11. 防超卖 DB 层的说法（**表达要精确，避免歧义**）
- ✅ **保险说法**（主动这么说）：
  > **"一条 UPDATE 语句：`SET stock = stock - 1 WHERE id = ? AND stock > 0`。判断和扣减写在同一句里；MySQL 执行 UPDATE 时【自动】加行锁保证原子，`stock > 0` 保证不减成负数。"**
- ⚠️ **通俗说法**："用行锁锁住商品 + 条件判断 stock>0" —— **理解上不算错**，但**有歧义风险**（面试官可能理解成"先锁再判断"）→ **建议主动补一句"是一条 SQL，不是两步"**
- ❌ **真正错的**：**"先 `SELECT ... FOR UPDATE` 加锁，再 `UPDATE`"** ← 这是 **check-then-act（先查后改）**，**正是超卖的根源**
- **口诀**：**"一条 UPDATE，判断和扣减写在一起；行锁是 MySQL 自动加的，不是我主动锁的"**
- **⚠️ 别和间隙锁混**：**间隙锁 = RR 当前读防幻读（防插入）**；**防超卖 = 行锁 + `stock>0` 条件更新**（两个不同用途）

### 两段 Lua 别混！❓
| Lua | 判断什么 | 挡哪种请求 |
|---|---|---|
| **STOCK_LUA**（库存预减）| 库存够不够 | 挡"**买不到**的"（防超卖、保护 DB）|
| **TOKEN_BUCKET_LUA**（令牌桶）| 单位时间请求次数 | 挡"**太快/太频**的"（限速、防刷）|
> 两个都在"挡流量"，角度不同：**令牌桶管速度(次数)，库存预减管数量(库存)**。

## 六、死锁（2026-09-06 记反过"不可剥夺"，重点记）
四条件口诀：**"互请不可循"**（互斥 / 持有并等待 / 不可剥夺 / 循环等待）

互斥 -- 不可破坏
持有并等待 -- 允许破坏（一次申请所有）
不可剥夺 -- 不能被抢，只能自己释放/允许被剥夺资源
循环等待 -- 编号按序申请

- ⚠️ **不可剥夺** = 资源**不能被抢**，只能**自己释放**（"不可"+"剥夺"=不能抢）。曾记反成"能抢"。
- 解法破坏一键对应：①互斥(破不了) ②持有等待→一次申请所有 ③不可剥夺→允许剥夺/锁超时tryLock ④循环等待→编号按序申请

## 七、令牌桶（2026-09-08 学，见《限流-令牌桶.md》）
- **令牌桶 vs 秒杀库存**：令牌桶**会自动补令牌**(elapsed×rate)，库存**只减不补**(售罄没了)。这是两者核心区别。
- 令牌桶：capacity(容量·突发能扛) + rate(速率·长期上限)；取1令牌过了就扣，没令牌→限流(429)
- Redis 存令牌 → 分布式全局限流（多实例共享同一份状态）
- ⚠️ 会说错词：单机计数问题是"**多实例**"各记各的，不是"多线程"（单机多线程用AtomicInteger没问题）。面试说"多实例部署需Redis共享状态做分布式限流"
- Lua 存桶用 HMGET/HSET(Hash存tokens+last_refill)；补令牌公式 `math.min(capacity, tokens + elapsed*rate)`
- key 由 Java 调用时传（不在 Lua 写死）

## 八、集群 & 分布式（2026-09-17 部署 Hadoop 集群时学）
- **集群** = 多台机器组队，两个目的：**① 扛更大负载**（性能/容量）**② 高可用**（一台挂了有备份）
- **主节点指挥**（Hadoop NameNode 管元数据/ResourceManager 管调度）、**从节点干活**（DataNode 存数据）
- **集群 vs 分布式**：集群=多台机器的**物理形态**；分布式=任务/数据**分散到多台处理**的工作方式
- **集群 vs 单机**：集群是分布式系统的**硬件基础**（Redis 集群、MySQL 主从集群同理）

## 九、CAP 定理（2026-09-19 学，曾把 CP/AP 举例答反）
- C 一致性 / A 可用性 / P 分区容错；**P 必须选**（网络分区必然发生）→ 实际是 **CP vs AP** 取舍
- ⚠️ **CP**：分区时**宁可拒绝服务也保一致** → 例：**ZooKeeper、Redis 集群**
- ⚠️ **AP**：分区时**宁可返回可能过期的数据也保可用** → 例：**Eureka（注册中心）、Cassandra**
- 争的不是"新旧"，是"**分区时要不要拒绝服务**"。C 是"一致"不是"新"。

## 十、MQ（2026-09-22 ~ 09-24 边做边学）

### 10.1 交换机 vs 队列 ⚠️（复用规则）
- **交换机** = "分拣中心" → **天生公用，可复用**（多条链路的死信都汇到 `seckill.dlx`）
- **队列** = "终点" → **一个用途一个队列，不可复用**
- **交换机的"一对多"** = 写**多条绑定**，每条指向**不同队列**（不是同一个队列绑两次！）
  - ⚠️ 曾犯：同一队列 `seckillDlq` 绑两次（dlq key + timeout key）→ 两个路由键都进球同一队列 = 没区分

### 10.2 生产者重试 vs 消费者重试 ⚠️
| | 配置 | 管什么 |
|---|---|---|
| **生产者重试** | `spring.rabbitmq.template.retry.*` | 消息**发送失败**重发 |
| **消费者重试** | `spring.rabbitmq.listener.simple.retry.*` | 消息**处理失败**重试 |
- ⚠️ 两者完全不同，别配错地方
- ⚠️ `listener.simple.retry.enabled` **默认 false**！不显式写 `true`，整个 retry 配置**静默失效**

### 10.3 ack 模式：none / auto / manual ⚠️（陷阱题）
| 模式 | 行为 |
|---|---|
| `none` | 纯自动：**投递即 ack**（方法还没执行完就 ack）→ 异常则**消息丢失** |
| **`auto`（Spring 默认）** | **AOP 拦截**：方法正常返回→ack；**抛异常→nack 重入队** |
| `manual` | 完全自己调 `basicAck/nack` |

- ⚠️ **面试陷阱**："自动 ack 不是会丢消息吗？" → 你说的"自动 ack"是 `none`；**Spring 的 `auto` 不同**。名字像，机制完全不同。
- **重试耗尽** → Spring 抛 `AmqpRejectAndDontRequeueException` → **这才是死信的触发点**

### 10.4 死信的两种产生方式
| 方式 | 触发 | 用途 |
|---|---|---|
| **消费失败**（nack/reject，requeue=false） | 重试耗尽 | 可靠性兜底 |
| **消息 TTL 过期** | 消息躺够时间 | **实现延迟队列** |

- **TTL + DLX = 延迟队列**（RabbitMQ 无原生延迟消息）

### 10.4b ⭐⭐ 死信转移：谁"搬运" vs 谁"分拣"（2026-09-28，2 次答错）

**核心：这是【两步】，不是一步。**

| 步骤 | 谁做 | 依据什么 |
|---|---|---|
| **① 检测过期 + 投递**（搬运） | **RabbitMQ 内核** | 读**队列参数** `x-message-ttl`、`x-dead-letter-exchange`、`x-dead-letter-routing-key` |
| **② 按地址分到队列**（分拣） | **死信交换机** | 读 `routingKey` + 自己的**绑定表** |

**口诀**：
- **搬运 = RabbitMQ 内核**（读**队列参数**）
- **分拣 = 交换机**（读 **routingKey**）
- ⚠️ **交换机根本不知道"时间"** —— TTL 是**队列参数**，由**内核**检查

**追问自测**：谁决定"躺 30 分钟"？
→ **不是交换机**。是① `x-message-ttl`（规则，写在队列参数里）+ ② RabbitMQ 内核（执行）

**⚠️⚠️ 顺序别反（2026-09-29 答反过）**：

```
✅ 正确：delay.queue → 死信交换机 seckill.dlx → timeout.queue
❌ 答反：delay.queue → timeout.queue → 死信交换机
```

**记忆锚点**：
> **交换机永远是"中转站"，不是"终点"。**
> **消息必须先到交换机，才能被路由到队列** —— 队列不会直接跳到另一个队列。

**面试话术**：
> "TTL 过期后，**RabbitMQ 检测到消息过期**，按队列声明的 `x-dead-letter-exchange`
> 和 `x-dead-letter-routing-key` **投递**到死信交换机，**死信交换机再按 routingKey
> 路由**到最终的处理队列。所以 **RabbitMQ 是搬运方，交换机只是分拣中心**。"

### 10.5 延迟队列 vs 超时处理队列 ⚠️（最容易混）
| | 延迟队列 | 超时处理队列 |
|---|---|---|
| **比喻** | **候诊区**（坐着等） | **诊室**（进来就干活） |
| **有消费者吗** | ❌ **故意没有** | ✅ 有 |
| **参数** | `x-message-ttl` + `x-dead-letter-*` | 无 |
| **作用** | 让消息躺着等 TTL | 真正处理 |

- **核心洞察**："延迟"能力 = **故意不配消费者**（消息没人取 → 一直躺 → 躺到过期）
- ⚠️ 不能用"消费者 sleep 30 分钟"代替：会**阻塞消费者**（吞吐归零）+ 重启丢失 + 不精确

### 10.6 即时消息 vs 延迟消息 ⚠️（处理方式的本质区别）
| | 即时消息 | 延迟消息 |
|---|---|---|
| **发送时状态** | **已知** | **未知**（30分钟后才知道） |
| **处理时** | 直接处理 | **必须重新查状态** |

- **为什么**：延迟消息是 30 分钟前发的，这期间用户**可能已经付款** → 不查状态就取消 = **事故**
- **口诀**：**延迟消息 = 对"未来状态"的操作，处理时必须以"当前实际状态"为准**

### 10.7 业务失败 vs 系统失败（决定要不要重试）⚠️
| 类型 | 表现 | 该怎么做 |
|---|---|---|
| **业务失败** | `rows == 0`（状态已变/幂等） | **不重试**（业务上就不该做） |
| **系统失败** | **抛异常**（DB 挂了/超时） | **抛出→MQ 重试**→仍失败→死信队列 |

- **关键**：`rows == 0` **大部分是"正常"的**（用户付款了/重复消息）→ **不能靠它判断要不要重试**
- **只有抛异常才是真失败** → 用 try-catch 区分

### 10.8 数据模型 ↔ 操作方法 映射 ⚠️（写代码卡住的原因）
| 做什么 | 数据在哪 | 用什么 |
|---|---|---|
| 落订单 | `seckill_order`（**加一行**） | `insert` |
| 取消/支付订单 | `seckill_order.status`（**改字段**） | `update` |
| 扣/还库存 | `seckill_goods.stock`（**改字段**） | `update`（`stock±1`） |
- **口诀**：**订单是"行"用 insert；库存是"字段"用 update**
- 库存更新用**原子更新** `SET stock = stock + 1`，**不要"先查后改"**

### 10.9 ⭐ 卫语句（guard clause）模板 —— MQ 消费者万能结构
```java
public void consume(String msg) {
    // 1. 解析 + 校验：格式不对 → return
    if (格式不对) return;
    // 2. 查数据：查不到 → return
    if (data == null) return;
    // 3. 状态判断：把"不该继续"的全部 return 掉
    if (不该继续1) return;
    if (不该继续2) return;
    // 4. 剩下的就是"该干活"的 → 直接写业务（不用再 if）
    doBusiness();
}
```
- **心法**：写 `if` 时先问 —— **"这个条件成立，我是要【做事】还是要【滚蛋】？"**
  - **要滚蛋 → `return`**
  - **要做事 → 不写 `if`，直接往下写业务**
- ⚠️ **曾犯**：把"该做事"的分支（status==0 待支付）也 `return` 了 → **永远走不到后面的 cancel**
- ⚠️ 另一个曾犯：**"状态名"当成"动作"**（打印"待支付"就 return）—— "待支付"是**状态**，"取消订单"才是**动作**

### 10.10 快速验证技巧（TTL 太长怎么办）
- **把 TTL 临时改成 10 秒**（`10 * 1000`）验证 → 通过后改回真实值
- ⚠️ **TTL 是队列参数，改完必须删旧队列**（`rabbitmqctl delete_queue`），否则启动报 `PRECONDITION_FAILED`
- ⚠️ **PowerShell 改文件容易引入 BOM**（`\ufeff`）→ 用 `[System.IO.File]::WriteAllText($f,$c,(New-Object System.Text.UTF8Encoding($false)))`

### 10.11 ⭐⭐ 可靠性三题（2026-09-25，高频面试）

#### 题1：`rows == 0` 为什么不抛异常（不重试）？
- **`rows == 0` = "业务拒绝"**，两种原因都正常：
  - 用户**抢先付款**了（状态 0→1，`WHERE status=0` 匹配不到）
  - 消息**重复投递**（状态已是 2）
- **重试的定义**：*"可能因临时故障失败，再试一次可能成功"*
- **`rows == 0` 重试 100 次还是 0** → **重试无意义**
- **口诀**：
  - **`rows == 0`（确定性失败/业务拒绝）→ 不重试**
  - **抛异常（临时故障）→ 才重试**

#### 题2：为什么 `throw new RuntimeException(msg, e)` 不能 `throw e`？
- **Java 受检异常机制**：方法**未声明 `throws`** 就**不能抛受检异常**
- `Exception`/`IOException`/`SQLException` = **受检**；`RuntimeException` = **非受检**
- `@RabbitListener` 的方法签名**固定**（`void consume(String)`），**不能加 `throws`**
- → 所以**把受检异常包装成 `RuntimeException` 抛出**
- **第二个参数 `e` 必须传**：保留原始堆栈（否则日志只见"业务异常"，看不到真正原因）
- **专业名词**：**异常转译（exception translation）** ← 面试可讲

#### 题3：⚠️ ①成功②失败 = 数据不一致（最重要）
```java
try {
    cancel(orderNo);      // ① status: 0 → 2
    addStock(goodsId);    // ② stock + 1  ← 这里失败
} catch (Exception e) { throw ...; }   // → MQ 重试
```
- **第 1 次**：①成功（已提交）→ ②失败 → 抛异常 → 重试
- **第 2 次**：①`rows = 0`（status 已是 2）→ **`return`** → ②**永远不执行**
- **结果**：订单已取消 ✅ 但**库存永久少 1** ❌ = **数据不一致**
- **根因**：**①②是【两个独立事务】，不是原子的**
- **解法**：**加 `@Transactional`** → ②失败时**①一起回滚** → 重试时两步重做 → **要么全做要么全不做**
- ⚠️ `@Transactional` 坑：**同类调用/private 方法 → 事务失效**（学过的 Spring 事务失效场景）

#### 重试机制的完整图景
```
业务失败（rows==0）→ 正常结束（ack）
                               ┌─ 成功 → 结束
系统失败（抛异常）→ MQ 重试 3 次 ┼─ 失败 → 重试
                               └─ 仍失败 → 进死信队列（DLQ）→ 人工/补偿
```
- **"死信队列"就是为"系统失败重试耗尽"兜底的** ← 面试连起来讲
