# 短链接项目深挖 — 面试防御手册

> 用途：每次面试的"项目深挖"环节都靠它。这 5 问全部要能脱口而出。
> 简历承诺的每个数字都要能解释来源：缓存命中率 70%+、DB QPS 降 60%、联调降 30%。

---

## Q1 短码方案：为什么"自增ID + Base62"，不用 UUID / 分布式锁？

**答**：短码要"又短又唯一"。UUID 唯一但 32 位太长，直接排除；分布式锁能保证唯一，但每次生成都要锁协调，高并发下是瓶颈。用数据库自增 ID——**唯一性交给 MySQL 自增保证，应用层零协调、零锁竞争，吞吐高**。

追问链（代价要主动说，面试官必追问）：
- **先插后更**：INSERT 拿 ID 再 UPDATE 回写短码，多一次写
- **依赖单库自增**：分库分表后自增 ID 会撞 → 演进成雪花算法
- **短码可枚举**：自增规律可被遍历 → 在意隐私要加随机化/打散

**记忆锚**：UUID 太长、锁太慢、自增交给 DB。

## Q2 缓存：命中率怎么来的？穿透/击穿/雪崩？

**答（数据口径，数字统一"300 万"）**：造了 300 万条测试数据压测对比——走 Redis 缓存接口 vs 直接查 MySQL 接口，**DB QPS 下降约 60%**；命中率 70% 看日志：**70% 请求命中缓存，30% 回源**。

三兄弟（背）：
- **穿透**（数据不存在）：缓存空值 / 布隆过滤器
- **击穿**（单个热点 key 过期瞬间）：互斥锁（只让一个请求重建）/ 逻辑过期
- **雪崩**（大批 key 同时过期）：过期时间加随机值 / 多级缓存（本地+Redis）/ 限流降级

收尾加分：*"我的项目主要防穿透——查不存在的短码，把空值也缓存。"*

---

## Q3 异步日志：为什么 AOP + 线程池？

**答**：同步写 = 请求线程自己写库，每次跳转多一次 DB 写，高并发下接口被拖垮。AOP 是横切关注点，日志采集不污染业务代码。异步 = **主线程把任务丢给线程池立即返回，后台线程写库**，主链路不受影响。

追问链：
- 线程池参数？→ core / max / 队列 / 存活时间 / 线程工厂（要能说清自己怎么定的）
- 队列满了？→ core 满 → 进队列 → 队列满 → 开非核心线程 → 全满 → **拒绝策略**
- 日志丢了？→ 日志是非核心数据，队列有界，优先 CallerRunsPolicy 保证不丢，极端允许丢弃——**绝不让日志拖垮主业务**

## Q4 TopN：为什么用 ZSet？

**答**：TopN 是排行榜场景，ZSet 量身定做。每次访问 **ZINCRBY** 原子加一，查询 **ZREVRANGE** 倒序取前 N。不用 MySQL 是因为实时排序对 DB 压力大（适合定时任务离线算日报）。

**底层**：哈希表（O(1) 找 member→score）+ 跳表（O(logN) 排序）。

---

## Q5 全局异常处理器？

**答**：`@RestControllerAdvice`（= @ControllerAdvice + @ResponseBody）定义全局异常处理器，`@ExceptionHandler` 分别处理业务异常和兜底异常，统一返回 `{code, message, data}`。业务异常给明确提示，系统异常兜底"系统繁忙"，不泄露堆栈。**格式统一，所以联调时间降了 30%**。

追问链：
- 和 @ControllerAdvice 关系？→ @RestControllerAdvice = @ControllerAdvice + @ResponseBody
- 异常匹配优先级？→ 精确匹配优先（BusinessException 先于 Exception）
