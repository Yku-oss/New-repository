### 重点知识点拆解
```
    ① HashMap 底层原理（必问）
        · JDK7：数组 + 链表          JDK8：数组 + 链表 + 红黑树
        · put 流程：计算 hash → 定位桶 → 冲突拉链 → 链表≥8 且数组≥64 转红黑树
        · 扩容机制：默认容量 16，负载因子 0.75，扩容时 rehash
        · 为什么容量是 2 的幂？→ 位运算 (n-1)&hash 代替取模，性能高
        · 为什么转红黑树阈值是 8？→ 泊松分布，链表长度 8 概率极低
        · 线程不安全表现：JDK7 扩容死循环、JDK8 数据覆盖丢失

    ② 集合框架对比（什么场景用什么）
        · ArrayList（数组，随机访问快）  vs  LinkedList（链表，增删快，但内存开销大）
        · HashMap（无序） vs TreeMap（有序，红黑树） vs LinkedHashMap（插入顺序，LRU 缓存）
        · HashSet 底层就是 HashMap（value 用固定对象）
        · HashMap vs Hashtable vs ConcurrentHashMap（线程安全区别）
        · 并发场景：HashMap 不安全 → 用 ConcurrentHashMap（分段/桶锁）
        · 迭代时能否修改？→ fail-fast（ConcurrentModificationException）

    ③ == 与 equals / hashCode（必问）
        · == 比较引用地址；equals 默认也是地址，重写后比较内容
        · 重写 equals 必须重写 hashCode（HashMap 查找依赖）
        · hashCode 相同 → equals 不一定相同（冲突）；equals 相同 → hashCode 必相同

    ④ String 相关
        · String 不可变（final，字符数组）→ 线程安全、可缓存
        · StringBuilder（线程不安全，快） vs StringBuffer（synchronized，慢）
        · 字符串常量池（JDK7 移到堆中）、intern() 方法

    ⑤ 面向对象
        · 重载（编译期，参数列表不同） vs 重写（运行期，继承）
        · 接口（多实现，默认方法） vs 抽象类（单继承，可有状态）
        · static（类级别） / final（不可变）/ transient（不序列化）

    ⑥ 异常体系
        · Throwable → Error（不可处理） + Exception
        · 受检异常（编译期，必须处理） vs 非受检异常（运行期 RuntimeException）
        · try-with-resources（自动关闭资源）

    ⑦ 泛型与反射
        · 泛型擦除（编译期去类型）
        · 反射：Class.forName、getMethod、invoke；性能低，框架用
```
## JVM 
```
    主要是JVM调优，OOM遇到各种情况该怎么做，怎么排查，理解其他机制的内容即可
```

### 重点知识点拆解
```
    ① 运行时内存结构
        · 堆（Heap）：新生代（Eden + 2×Survivor）+ 老年代，对象都在这
        · 方法区/元空间（Metaspace，JDK8 起本地内存，存类元信息、常量池）
        · 虚拟机栈（栈帧：局部变量表、操作数栈）、本地方法栈、程序计数器
        · 堆内存比例：新生代 : 老年代 = 1 : 2，Eden : S0 : S1 = 8 : 1 : 1

    ② 对象创建与布局
        · 创建过程：类加载检查 → 分配内存（指针碰撞/空闲列表）→ 初始化零值 → 设置对象头 → init
        · 对象头 Mark Word：存 hashcode、GC 分代年龄、锁状态标记

    ③ 垃圾回收（GC）
        · 可达性分析：GC Roots（栈引用、静态变量、常量、JNI）
        · 四种引用：强引用（不回收）、软引用（内存不足回收）、弱引用（GC 即回收）、虚引用
        · 三大算法：标记清除（碎片）、复制（新生代）、标记整理（老年代）
        · 分代回收：Minor GC（新生代）/ Major GC（老年代）/ Full GC（整堆）

    ④ 垃圾收集器
        · Serial/Parallel（并行）/ CMS（并发标记清除，低延迟）/ G1（默认，分区+可预测停顿）
        · G1 特点：Region 分区、跨代回收、可设置最大停顿时间 -XX:MaxGCPauseMillis
        · 如何选择：追求吞吐用 Parallel，追求低延迟用 G1/ZGC

    ⑤ 类加载机制
        · 生命周期：加载 → 验证 → 准备 → 解析 → 初始化 → 使用 → 卸载
        · 双亲委派模型：Bootstrap → Extension → Application，父加载不了才自己加载
        · 为什么要双亲委派？→ 防止核心 API 被篡改（如自定义 java.lang.String）
        · 破坏双亲委派：SPI（ServiceLoader）、Tomcat（隔离不同 webapp）

    ⑥ OOM 排查（重点）
        · 堆溢出 java.lang.OutOfMemoryError: Java heap space
            → jmap -dump:format=b,file=xxx.hprof <pid> → MAT/Eclipse 分析大对象
        · 栈溢出 StackOverflowError → 死递归，-Xss 调大
        · 元空间溢出 Metaspace → 大量动态生成类（CGLIB 代理滥用）
        · 直接内存溢出 → NIO DirectBuffer 未释放

    ⑦ 调优工具与参数
        · 命令行：jps（进程）、jstack（线程栈，查死锁）、jmap（堆）、jstat（GC 统计）、jinfo
        · 图形化：jconsole、VisualVM、Arthas（阿里，线上神器）
        · 常用参数：-Xms/-Xmx（堆初始/最大）、-Xmn（新生代）、-XX:MaxMetaspaceSize
        · 调优思路：先看 GC 频率与停顿 → 调整堆大小 → 换收集器 → 排查代码问题（大对象、泄漏）
```

## Mysql
```
    Mysql主要是知道结合相关场景去理解
        要掌握三招绝杀慢SQL ： explain看type和rows，解决filesort文件排序，会手动修正优化器选错索引
        还有一些sql调优等
```

### 重点知识点拆解
```
    ① 索引（核心）
        · B+Tree 结构：多路平衡树，叶子节点存数据且链表相连（范围查询快）
        · 为什么用 B+Tree 不用 B-Tree/红黑树？→ 高度低（3 层可存千万级）、叶子链表支持范围查询
        · 聚簇索引（主键，叶子存整行） vs 非聚簇索引（二级索引，叶子存主键值）→ 回表
        · 联合索引最左前缀原则：a,b,c 联合索引，(a)、(a,b) 能用，(b) 用不上
        · 覆盖索引：查询列都在索引里，不用回表（优化利器）
        · 索引失效场景：like '%x'、函数运算、隐式类型转换、or 连接、最左前缀不满足

    ② 事务与隔离级别
        · ACID：原子性、一致性、隔离性、持久性
        · 4 种隔离级别：读未提交 → 读已提交 → 可重复读（MySQL 默认）→ 串行化
        · 问题：脏读、不可重复读、幻读
        · MySQL 默认可重复读 + MVCC + 间隙锁 解决幻读

    ③ MVCC（必问）
        · 隐藏字段：trx_id（事务 id）+ roll_pointer（回滚指针）
        · undo log 版本链 + ReadView（活跃事务列表）
        · 快照读（MVCC 不加锁） vs 当前读（加锁，如 select ... for update）

    ④ 三大日志
        · redo log：物理日志，崩溃恢复（WAL 先写日志再写数据）
        · binlog：逻辑日志，主从复制、数据恢复（两阶段提交保证一致性）
        · undo log：逻辑日志，事务回滚 + MVCC

    ⑤ 锁
        · 表锁 / 行锁（InnoDB 才有行锁）
        · 行锁类型：记录锁（record lock）、间隙锁（gap lock）、临键锁（next-key lock，默认）
        · 死锁：互相持有对方要的锁 → 排查 SHOW ENGINE INNODB STATUS

    ⑥ SQL 执行流程
        · 查询：连接器 → 查询缓存（已移除）→ 分析器 → 优化器（选索引）→ 执行器 → 存储引擎
        · 更新：额外写 redo log（prepare → commit 两阶段）+ binlog

    ⑦ 慢 SQL 优化（你提到的三招）
        · 第一招：explain 看 type 和 rows
            type 从好到差：const → eq_ref → ref → range → index → ALL（全表扫描）
            rows 越大越慢，目标：type 至少到 range，最好 ref/const
        · 第二招：解决 filesort
            出现 Using filesort（extra 字段）→ 排序没走索引
            解决：给 ORDER BY 字段建联合索引，让排序走索引避免文件排序
        · 第三招：手动修正优化器选错索引
            用 FORCE INDEX(索引名) 强制走指定索引
            或调整语句（改写 join 顺序、加提示）让优化器选对

    ⑧ 常见优化手段
        · 避免 select *，只查需要的列（走覆盖索引）
        · 分页优化：limit 大偏移 → 用"上次最大 id"代替 offset
        · 小表驱动大表、join 字段建索引
        · 高频写场景：批量插入、减少不必要索引
```

## Redis
```
Redis要知道是一个非关系型数据库，了解其中的语法，知道怎么使用
    吃透缓存穿透，击穿，雪崩三层防护方案；
    分布式锁要了解SETNX，还有Redisson看门狗自动续期等

```

### 重点知识点拆解
```
    ① 五大基础数据结构
        · String（字符串）：缓存、计数器（INCR）
        · List（列表）：消息队列、最新列表
        · Hash（哈希）：对象缓存（用户信息）
        · Set（集合）：去重、共同好友（交集）、抽奖
        · ZSet（有序集合）：排行榜（分数排序）、延时队列
        · 底层编码：跳表（ZSet）、压缩列表（小数据）、快速列表

    ② 持久化
        · RDB：快照，二进制，恢复快但可能丢数据
        · AOF：追加日志，不丢数据但文件大
        · 实际生产：RDB + AOF 混用，AOF 每秒 fsync

    ③ 缓存三大问题（必问）
        · 缓存穿透：查不存在的数据，绕过缓存直接打 DB
            → 布隆过滤器拦截 / 缓存空值（null 也缓存，带短过期）
        · 缓存击穿：热点 key 过期瞬间，大量请求打到 DB
            → 互斥锁（只让一个线程去重建缓存）/ 逻辑过期（后台异步刷新）
        · 缓存雪崩：大量 key 同时过期 / Redis 宕机
            → 过期时间加随机值打散 / 多级缓存（本地+Redis）/ Redis 高可用（哨兵、集群）

    ④ 分布式锁（必问）
        · 基本实现：SET key value NX EX 30（原子命令，防死锁）
        · 问题一：锁过期了业务没执行完 → Redisson 看门狗自动续期
            Redisson 默认 30s 有效期，后台线程每 10s 检查续期
        · 问题二：加锁和释放锁要保证是同一个线程 → value 存唯一标识（UUID），释放时 Lua 脚本校验
        · 问题三：主从切换锁丢失 → RedLock（多节点加锁，过半成功）

    ⑤ 过期删除与淘汰策略
        · 删除策略：惰性删除（访问时检查）+ 定期删除（周期抽查）
        · 内存淘汰：LRU（最近最少用）、LFU（最不常用）、allkeys/volatile 维度
        · 生产配置：maxmemory-policy allkeys-lru

    ⑥ 高可用架构
        · 主从复制：一主多从，读写分离，主挂了从顶上来
        · 哨兵（Sentinel）：监控主从，自动故障转移
        · Cluster 集群：16384 个槽位，数据分片存储，多主多从
        · 缓存一致性：先更新 DB 再删缓存（延迟双删），或 binlog 订阅（Canal）异步删缓存
```


## Springboot
```
    需要吃透一条核心链路：Controller如何扫描和实例化，依赖注入bean；知道bean的声明周期，当收到请求时知道怎么给出结果；线程冲突或者不对时，知道怎么修改。
```

### 重点知识点拆解
```
    ① 核心链路（你提到的，必讲通）
        · @SpringBootApplication = @SpringBootConfiguration + @EnableAutoConfiguration + @ComponentScan
        · 扫描：@ComponentScan 扫描包路径下所有 @Component/@Service/@Repository/@Controller
        · 实例化：扫描到的类解析成 BeanDefinition → 反射创建实例
        · 依赖注入：@Autowired 按类型注入，@Resource 按名称注入
        · 收到请求：DispatcherServlet → HandlerMapping（找 @RequestMapping）→ Controller
            → Service → Mapper → 返回结果（JSON 序列化）→ 响应

    ② Bean 生命周期（必问）
        实例化 → 属性填充 → Aware 回调 → BeanPostProcessor 前置 →
        @PostConstruct → InitializingBean.afterPropertiesSet → 初始化方法 →
        BeanPostProcessor 后置（AOP 代理在这生成）→ 使用 → @PreDestroy → 销毁

    ③ Bean 作用域
        · singleton（默认，单例，线程不安全要注意）
        · prototype（每次新建）、request、session
        · 单例 Bean 里注入多例 Bean 的问题：注入的是同一个，需用 @Scope(proxyMode)

    ④ 循环依赖与三级缓存（必问）
        · A 依赖 B，B 依赖 A
        · 三级缓存：一级（成品）→ 二级（早期对象）→ 三级（ObjectFactory 工厂）
        · 解决：先暴露早期引用（半成品）让 B 注入，B 完成后再填充 A
        · 构造器注入无法解决循环依赖（因为没有"半成品"可暴露）

    ⑤ AOP
        · 动态代理：JDK 代理（接口） vs CGLIB（子类，无接口用）
        · 通知类型：@Before / @After / @Around / @AfterReturning / @AfterThrowing
        · 事务注解失效场景（必问）：
            自调用失效（同类里 this 调用不走代理）
            方法非 public、被 final/static 修饰
            异常被 try-catch 吞掉不抛出
            抛出的是检查异常（默认只回滚 RuntimeException）

    ⑥ Spring MVC 执行流程
        DispatcherServlet → HandlerMapping → HandlerAdapter → 拦截器 → Controller
        → ModelAndView → ViewResolver → 渲染 → 响应

    ⑦ 自动配置原理
        · @EnableAutoConfiguration → 加载 META-INF/spring.factories 里的 AutoConfiguration
        · 条件注解：@ConditionalOnClass / @ConditionalOnProperty / @ConditionalOnMissingBean
        · 面试话术：Spring Boot 通过 SPI 机制加载所有自动配置类，再按条件注解判断是否生效

    ⑧ 线程冲突排查（你提到的）
        · 单例 Bean 内有状态字段 → 多线程共享，出现数据错乱
        · 解决：Controller/Service 不要存状态字段，局部变量用完即弃
        · 使用 ThreadLocal 存上下文时，记得 finally remove() 防泄漏
```

## MQ
```
两个大问题：
    消息丢失怎么兜底？
    消息积压怎么处理？
再有就是知道怎么调优等
```

### 重点知识点拆解
```
    ① 消息丢失的三种场景与兜底（必问）
        · 生产者丢失：
            → 开启 confirm 确认机制（发出去等 ack，没 ack 就重发）
            → 事务消息（性能低，confirm 为主）
        · Broker 丢失：
            → 持久化（队列 + 消息都 durable）
            → 刷盘策略（RocketMQ 同步刷盘，Kafka acks=all）
        · 消费者丢失：
            → 关闭自动 ack，消费成功后再手动 ack
            → 消费失败重试，重试多次进死信队列人工处理

    ② 消息积压怎么处理（必问）
        · 为什么积压：消费者处理慢 / 消费者挂了 / 生产者瞬时洪峰
        · 解决思路一：扩容消费者（水平扩展，注意队列数要 >= 消费者数）
        · 解决思路二：临时队列转存（先攒起来，慢慢消费，不丢业务）
        · 解决思路三：批量消费 + 优化消费逻辑（合并 DB 操作）
        · 核心：先保证不丢消息，再恢复消费能力，最后补齐积压

    ③ 消息重复消费（必问）
        · 原因：网络抖动 ack 丢失、消费端超时重试 → 消息被投递多次
        · 解决：消费端幂等
            → 唯一业务 ID + 数据库唯一约束（最可靠）
            → Redis SETNX 去重标记
            → 状态机校验（订单状态判断是否已处理）

    ④ 消息顺序性
        · 全局有序很难，一般保证局部有序
        · 方案：同一业务 key（如订单号）路由到同一个队列/分区
        · 消费者单线程消费该队列

    ⑤ 死信队列与延时消息
        · 死信队列：消费失败 N 次 / 过期未消费 → 进死信，人工或定时重放
        · 延时消息：RocketMQ 自带延时级别；RabbitMQ 用死信 + TTL 实现

    ⑥ MQ 选型对比
        · RocketMQ：阿里，功能全（事务消息、延时、死信），Java 生态，中小厂常用
        · Kafka：高吞吐、日志/大数据场景，可靠性稍弱（副本机制可补）
        · RabbitMQ：功能简单易用，吞吐低于前两者
        · 场景：业务消息用 RocketMQ/RabbitMQ，日志/埋点/大数据用 Kafka

    ⑦ 调优方向
        · 生产者：批量发送、压缩、异步发送
        · 消费者：合理并发数（和队列数匹配）、批量拉取
        · Broker：页缓存、磁盘顺序写、刷盘策略权衡（吞吐 vs 可靠性）
```

## 分库分表
```
    吃透Sharding核心配置，分片规则，跨分片查询兜底方案
```

### 重点知识点拆解
```
    ① 为什么分库分表
        · 单表数据量过大（千万级+）→ 索引失效、查询变慢
        · 单库连接数瓶颈、单库容量瓶颈
        · 前提：先优化（索引、缓存、读写分离），数据量大到一定程度才分

    ② 拆分方式
        · 垂直拆分：按业务拆库（订单库/用户库/商品库），按字段拆表（大字段单独放）
        · 水平拆分：按规则把数据分散到多个表/库
            → 取模（均匀，扩容要迁移）、范围（连续，易倾斜）、一致性哈希（扩容平滑）

    ③ ShardingSphere 核心配置（重点）
        · 数据源配置：多个数据源（ds0、ds1...）
        · 分片规则：分片键（sharding-column）+ 分片算法（inline 表达式、自定义）
        · 绑定表：订单表和订单明细表用相同分片键，join 时不跨库
        · 广播表：所有库都有一份的表（如配置表），无需分片
        · 分片策略：标准分片 / 复合分片 / Hint 分片（强制路由）

    ④ 跨分片查询兜底方案（必问）
        · 问题一：分布式主键
            → 雪花算法（Snowflake）：时间戳 + 机器号 + 序列号，全局唯一且有序
        · 问题二：跨分片聚合/排序
            → 各分片先查 → 中间层聚合（ShardingSphere 自动做）
            → 或者数据冗余（宽表），避免 join
        · 问题三：分布式事务
            → 强一致：XA 两阶段提交（性能低）
            → 最终一致：本地消息表 / MQ 事务消息 / Seata（AT 模式，推荐）
        · 问题四：全表扫描查询
            → 带分片键查询直接路由；不带分片键 → 广播到所有分片再合并（慢，尽量避免）

    ⑤ 中间件对比
        · ShardingSphere-JDBC：客户端分库分表，集成简单，应用内分片
        · ShardingSphere-Proxy：独立代理服务，对应用透明
        · MyCat：独立中间件，性能一般，社区活跃度下降
```

## 场景问题
```
    秒杀系统怎么拦截，库存怎么扣减，订单怎么落盘，数据怎么拆分，每层技术选型，优劣对比烂熟于心
    消息分布平台 ：海量消息怎么接入，存储，推送，失败怎么补偿，最终一致性怎么保证，定时对账怎么实现
```

### 场景一：秒杀系统（必问，全链路）
```
    ① 前端拦截（挡掉大部分流量）
        · 按钮置灰、验证码/滑块、答题
        · 每用户限购一次（前端 + 后端双重校验）

    ② 入口限流（挡掉恶意流量）
        · Nginx/LVS 负载均衡 + 限流（IP 限流、令牌桶）
        · 网关层（Sentinel/Guava RateLimiter）接口限流

    ③ Redis 拦截 + 预扣库存（挡掉无效请求）
        · 布隆过滤器：拦截不存在的商品 ID（缓存穿透防护）
        · 库存预热到 Redis：DECR 原子扣减，扣到 0 直接返回"已抢完"
        · 只有扣减成功的人才进入下单流程 → 大幅减少对 DB 的冲击

    ④ MQ 异步削峰（解耦 + 缓冲）
        · 扣减成功 → 发消息到 MQ → 消费者异步落订单
        · 好处：请求处理变快、削峰填谷、DB 压力可控

    ⑤ MySQL 最终落库（保证一致性）
        · 先扣库存再生成订单（防止超卖）
        · 扣库存用乐观锁：UPDATE stock SET num = num - 1 WHERE num > 0（原子条件更新）
        · 订单 + 库存 + 流水 事务保证

    ⑥ 兜底与一致性
        · 失败补偿：消息失败重试 + 定时对账（扫描超时未支付订单释放库存）
        · 最终一致性：本地消息表 / MQ 事务消息

    ⑦ 技术选型对比
        · 为什么用 Redis 扣库存不用 MySQL？→ 吞吐量差 10 倍以上，Redis 单线程原子性
        · 为什么用 MQ 不用同步调用？→ 削峰填谷，防止下游被瞬间打垮
        · 库存放 Redis 会丢吗？→ 会（宕机），所以最终以 DB 为准，Redis 只是"预扣"
```

### 场景二：消息推送平台（海量消息）
```
    ① 海量消息怎么接入
        · 生产者 → MQ（Kafka/RocketMQ），分区并行
        · 批量发送、压缩、异步

    ② 怎么存储
        · MQ 落盘（顺序写磁盘，吞吐高）
        · 消息持久化 + 过期清理策略（按 topic 保留 N 天）

    ③ 怎么推送
        · 推送服务多实例 + 负载均衡
        · 按设备数分片（分桶），每个桶一个消费线程
        · 推送下游（APNs/极光/自建长连接）限速，避免被打爆

    ④ 失败怎么补偿
        · 消费失败重试（指数退避）
        · 超过重试次数 → 死信队列 → 人工/定时任务重放
        · 推送失败记录到表 → 定时扫描重推

    ⑤ 最终一致性怎么保证
        · 消息表 + 状态字段（发送中/成功/失败）
        · MQ 事务消息：本地事务 + 消息一起提交
        · 对账兜底：即使消息丢了，定时对账也能发现并补发

    ⑥ 定时对账怎么实现
        · 定时任务（XXL-Job / Quartz）每天扫描
        · 比对：订单表 vs 消息表 vs 推送记录，找出不一致的
        · 差异处理：补发消息 / 修正状态 / 人工介入
```

## 总结
```
    不要只会背概念，重点时会梳理，会讲解，会复盘！从请求接入到数据落盘，全链路要逻辑通顺即可。
```

### 全链路串联（面试终极武器）

把知识点串成一条完整的业务链路，面试时能顺下来基本就稳了：

```
    用户发起请求
        ↓
    Nginx（负载均衡/限流）
        ↓
    Spring Boot 网关（鉴权/限流/灰度）
        ↓
    Controller（接收参数）
        ↓
    Service（业务逻辑）
        ├── Redis（缓存：命中直接返回 / 未命中查库）
        ├── 分布式锁（并发写保护）
        ├── MQ（异步解耦、削峰）
        └── MySQL（主库写 / 从库读，慢 SQL 走索引）
        ↓
    数据落盘 + 返回结果
```
