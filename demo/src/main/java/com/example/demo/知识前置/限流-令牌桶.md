# 限流 · 令牌桶（Rate Limiting）

> 秒杀加深功能（2026-09-07/08 实战落地）。Redis + Lua 分布式令牌桶，全局限流。
> 面试价值：高并发秒杀除了防超卖，还要防"恶意刷接口" → 限流。令牌桶 = 面试高频。

---

## 一、为什么需要限流

- 秒杀接口若谁都能无限刷 → 恶意请求把 Redis/DB 打崩
- **限流** = 在单位时间内限制请求数量，超过就拒绝（429 Too Many Requests）

## 二、令牌桶思路（核心）

想象一个**桶**，按固定速率**不断放令牌**，桶满则溢出。
每次请求**取一个令牌**，**有令牌 → 通过；没令牌 → 拒绝（被限流）**。

```
令牌桶：[托][托][托][托]
        ↑ 每 1/rate 秒补 1 个
请求 → 取令牌 → 有→放行 / 没→限流
```

**两个参数**：
- `capacity`（桶容量）：桶最多装几个 → 决定**能扛多少突发**
- `rate`（补充速率 个/秒）：每秒补几个 → 决定**长期稳定速率上限**

**为什么用令牌桶（面试讲）**：
> 既能允许**合理突发**（桶里攒的令牌一下子可用），又限制**长期平均速率**（补令牌速度定上限）。比"固定窗口/简单计数器"更平滑，一有波动就全拒。

## 三、内存限流 vs 分布式限流

- **单机内存**：普通计数器在 JVM 里，**多个服务实例各记各的 → 限不住总量**
- **分布式（Redis）**：用 **Redis 存令牌**，所有实例**共享** → 全局一致限流

## 四、Lua 脚本（原子实现）

把"取令牌"在 Redis 单线程里原子执行，避免并发多扣。

```java
private static final String TOKEN_BUCKET_LUA =
    "local key = KEYS[1] " +                       // key 由调用方传入(不在脚本写死)
    "local capacity = tonumber(ARGV[1]) " +        // 桶容量
    "local rate = tonumber(ARGV[2]) " +            // 补充速率(个/秒)，传的是参数列表
    "local time = redis.call('TIME') " +           // Redis 取当前时间(返回[秒,微秒])
    "local now = tonumber(time[1]) " +             // 取秒
    "local bucket = redis.call('HMGET', key, 'tokens', 'last_refill') " +  // 读桶状态:现有令牌+上次补充时间
    "local tokens = tonumber(bucket[1]) " +
    "local last = tonumber(bucket[2]) " +
    "if tokens == nil then tokens = capacity end " +   // 桶空→初始装满(允许突发)
    "if last == nil then last = now end " +
    "local elapsed = now - last " +                    // 距上次补令牌过了几秒
    "tokens = math.min(capacity, tokens + (elapsed * rate)) " +  // 补令牌,但不超过容量
    "if tokens >= 1 then " +
    "  tokens = tokens - 1 " +
    "  redis.call('HSET', key, 'tokens', tokens, 'last_refill', now) " +  // 扣1并记录时间
    "  return 1 " +                                   // 放行
    "else " +
    "  return 0 " +                                   // 被限流
    "end";
```

### 3 个陌生点（记忆）
1. **HMGET/HSET**：redis 存"多字段"（Hash）→ 桶存 tokens + last_refill 两个字段
2. **tonumber**：Redis 存的是字符串，要算得转数字
3. **补令牌逻辑**：`elapsed × rate` → 该补多少；`math.min(capacity, tokens+补的)` → 补但不超过容量

### key 由 Java 传（不写死）
脚本里 `KEYS[1]` 是占位，真正 key 是**调用时传**：
```java
public Long tryTokenBucket(String key, long capacity, long rate) {
    return stringRedisTemplate.execute(
        new DefaultRedisScript<>(TOKEN_BUCKET_LUA, Long.class),
        List.of(key),                      // 👈 key 在这里命名
        String.valueOf(capacity), String.valueOf(rate)
    );
}
```

## 五、接入秒杀接口（全局限流）

`doSeckillByRedis` **最开头**加（被限流的请求连 Redis 库存都不扣，最省资源）：
```java
Long allowed = tryTokenBucket("seckill:limit:all", 10, 5);  // 全局桶,容量10,每秒补5
if(allowed == null || allowed == 0){
    return Result.error(429, "请求过于频繁，请稍后重试");
}
```

**粒度选择**（key 决定限哪一级）：
- 全局限流：`seckill:limit:all`（一个桶，所有请求共享）
- 每用户：`seckill:limit:user:{userId}`
- 每商品：`seckill:limit:goods:{goodsId}`

## 六、实测结果（2026-09-08 验证）

- capacity=10, rate=5，连续发 **15 个请求**（不同用户）
- 结果：**成功 10 + 被限流 429 × 5**
- 符合预期：桶能扛突发 10，超过容量(短时来不及补)被挡 5

## 七、面试怎么讲这一块

> "秒杀接口还做了**令牌桶限流**防止恶意刷单。基于 Redis + Lua 原子实现：桶按固定速率(`rate`)补令牌、容量(`capacity`)控制突发，请求需取令牌才能通过，没有则返回 429。用 Redis 存令牌所以是**分布式**全局限流，多实例共享一致。相比简单计数器，令牌桶能允许合理突发又限制长期平均速率。"
